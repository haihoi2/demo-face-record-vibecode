# Agent handoff: ENTRY - detector input geometry for the wide entry gate area (rc2 P1)

## Task

- **Title:** Make entry faces detectable at the pipeline's frame budget: aspect-preserving detector
  input, tiling, and a dynamic-shape INT8 export, behind `PIPELINE_DETECT_INPUT`.
- **Owner/agent:** ENTRY (face-engine). Base `main` @ `89c7df0` (= `release/rt-pipeline`, v1.1.0-rt.1).
- **Acceptance criteria (from the brief):**
  1. The entry gate area (NVR-measured 3408x456 of the 4K picture; scripted 2074x432) reaches SCRFD at a
     scale where a 60 px face is found. Today it is letterboxed into a 640x640 square (scale 0.19 / 0.31),
     so a 60 px face arrives at ~11-18 px and shadow decided 0-2 of 36 entry persons.
  2. Implement, measure and recommend among (a) an aspect-preserving input within the 640x640 pixel
     budget, (b) overlapping 640-wide tiles merged with NMS, (c) an INT8 re-export with dynamic input.
  3. Wire the behaviour behind `PIPELINE_DETECT_INPUT` in the pipeline worker/onnxEngine only. The legacy
     engine's `detectFaces` defaults stay byte-for-byte identical (additive parameter, with a test).
  4. Keep the size floor semantics (60 px in SOURCE pixels).
  5. Measure with the MT replay harness on the entry clips (scripted and NVR): recall of >= 60 px faces
     per frame vs the FP32-1280 reference, entry shadow decisions per person-passage, frames/s, loop
     p50/p95, CPU. Unit tests for shape derivation, tile geometry, box/landmark mapping and merge.
- **Scope explicitly excluded:** `server.ts`, `db.ts`, `types.ts`, `contracts.ts`, `.env.example`,
  `docker-compose.yml`, `Dockerfile` (proposals below); tracker/decider thresholds; ArcFace.

## Changes

### Behaviour

- **`faceEmbedding.ts` (legacy engine: defaults unchanged).**
  - `detectFaces(input, options?: DetectOptions)`: the optional `inputShape: { width, height }` (multiples
    of 32) runs SCRFD at a non-square input. Without it the `FACE_DETECT_SIZE` square letterbox runs as
    before. `tests/detectShape.test.ts` keeps the previous square-only letterbox verbatim as a reference
    and proves the new one is byte-identical for every `FACE_DETECT_UPSCALE` mode, and (with models) that
    `detectFaces(img) deepEquals detectFaces(img, {inputShape: 640x640})`. `extractFaces`, the watcher,
    scan and recognize-face never pass options.
  - The anchor decode uses `gridW = W/stride`, `gridH = H/stride` (equal on the square path). Verified on
    the FP32 graph: 1824x224 yields 228x28x2 = 12768 stride-8 anchors, boxes in frame coordinates.
  - The engine reads the detector graph's input dims from the ONNX session metadata:
    `getFaceEngineInfo().detectorInputDims` = `{ width, height }` with numbers (static: the shipped INT8
    export is `640x640`) or `"dynamic"` (FP32 `det_10g` is `[1,3,?,?]`). A requested shape the graph
    cannot take returns `[]` with ONE log line per shape (no throw, no per-frame spam). The
    `engine ready` log line now names the dims.
  - `FACE_ORT_LOG_LEVEL` (0-4, default 2 = ORT's own default). Reason: `det_10g`'s output metadata is baked
    for 640x640, so at any other input ORT prints nine `Expected shape ... does not match` warnings per
    frame. The pipeline worker sets 3 for non-square plans; the legacy engine keeps 2.
- **`pipeline/detectInput.ts` (new, pure, deterministic).**
  - `parseDetectInput(raw)`: `""`/`square` (legacy), `auto`, `auto:<n>` (n x n budget, 320..2560),
    `<W>x<H>` (multiples of 32), `tiles:<n>[:<overlap%>]` (2..12, 0..50, default 20). Anything else is an
    ERROR (not silently ignored: silently running the geometry that lost every entry face is the failure
    this task fixes).
  - `deriveDetectShape(frameW, frameH, budgetPx)`: sides multiples of 32, product <= budget, never larger
    than the frame (no upscale), maximising `min(W/frameW, H/frameH)`, then trimmed to the smallest stride
    multiple holding the scaled picture (padding costs compute). 3408x456 -> 1696x224 (scale 0.491 instead
    of 0.188); 2074x432 -> 1408x288 (0.667 instead of 0.309); the exit area 1777x681 -> 1024x384 (0.564
    instead of 0.360); 1920x1080 -> 832x480 (0.433 instead of 0.333).
  - `tileGeometry(frameW, frameH, n, overlap)`: n integer tiles along the long axis, overlapping, the last
    one ending at the edge. `cropRgb`, `mapFromTile` (box + landmarks shifted by the tile origin),
    `mergeTileDetections` (the detector's NMS IoU, then a containment rule for the face one tile saw whole
    and its neighbour saw cut at the seam).
  - `detectWithPlan(detect, img, plan, {squareSize, nmsIou})` runs a plan and reports the resolved input.
  - `detectPlanIssue(plan, dims, squareSize, file)`: null when the loaded graph can run the plan, else the
    reason. `auto` needs dynamic dims; `<W>x<H>` needs dynamic dims or a graph exported at exactly that
    shape; `square`/`tiles` need the graph to take the `FACE_DETECT_SIZE` square.
- **`pipeline/onnxEngine.ts`.** Parses `PIPELINE_DETECT_INPUT` once, binds `detectWithPlan` to
  `detectFaces`. `ready()` is true only when the engine loaded AND the plan is compatible with the loaded
  graph; `error()` carries the reason (also logged once as `FAIL-CLOSED detector input: ...`). Logs one
  line when the resolved input changes (`detector input auto: 3408x456 frame -> 1696x224 (scale 0.49), 1
  run(s)/frame`). `detectInput()` describes the geometry for stats.
- **`pipelineCore.ts` / `pipelineProtocol.ts` / `gatePipeline.ts` (additive).**
  - `PipelineEngine.detectInput?()`; `WorkerStats.detectInput?`; `PipelineStats.worker.detectInput?`.
    `server.ts` logs `worker: st.worker` wholesale, so the stats line shows the geometry with no change.
  - `PipelineCore.applyContext`: when the engine is not ready, `contextReason` now includes the engine's
    own reason: `pipeline worker: face engine not ready (PIPELINE_DETECT_INPUT=auto needs a detector with
    dynamic input dims; det_10g_int8.onnx is static 640x640 ...)`. The existing `/face engine not ready/`
    assertions still hold.
  - `pipelineWorkerEnv`: `PIPELINE_DETECTOR_MODEL -> FACE_DETECTOR_MODEL` (a bare `*.onnx` file name in
    `FACE_MODEL_DIR`; paths and dotfiles are ignored), and `FACE_ORT_LOG_LEVEL=3` for `auto`/`<W>x<H>`
    plans unless set. The legacy engine's environment is untouched (the worker gets a copy).
- **Size floor.** The frame IS the gate area at native resolution, so `sizePx` (shorter box side in frame
  pixels) is in source pixels for every plan; boxes/landmarks are mapped back to frame coordinates before
  the tracker sees them. `FACE_MIN_SIZE_PX`/`clearFaceIssue` are unchanged.

### API/event contracts added or changed

- `FaceEngineInfo.detectorInputDims` (additive; shows on `/api/face-engine/status` `info`).
- `GatePipeline.stats().worker.detectInput` (additive, internal; appears in the per-gate stats log line).
- No SSE, route, schema or `types.ts` change.

### Environment/configuration (all optional; none is in `docker-compose.yml`/`.env.example` yet - proposal P1)

| Variable | Default | Effect |
|---|---|---|
| `PIPELINE_DETECT_INPUT` | `""` = legacy square | `auto` \| `auto:<n>` \| `<W>x<H>` \| `tiles:<n>[:<overlap%>]`; pipeline workers only; invalid = worker fails closed with the reason in stats |
| `PIPELINE_DETECTOR_MODEL` | inherit `FACE_DETECTOR_MODEL` | detector file in `FACE_MODEL_DIR`, pipeline workers only (e.g. `det_10g_int8_dyn.onnx`) |
| `FACE_ORT_LOG_LEVEL` | `2` | ORT session log severity 0-4; the worker sets 3 for non-square plans |

### Security/privacy impact

- No new data leaves the backend. Detections, crops and embeddings are unchanged in kind.
- Fail closed is stricter: an incompatible/invalid detector input plan stops the worker from deciding and
  says why. The legacy door path is untouched (`detectFaces` default path proven identical).
- `PIPELINE_DETECTOR_MODEL` accepts a file NAME only, so a worker cannot be pointed outside `FACE_MODEL_DIR`.
- Model artifacts stay on `/data/models` (never committed). Calibration tensors and cached frames were
  biometric derivatives in a 0700 scratch dir and are deleted (see Cleanup).

## Measurements

### Method

- **Offline, per frame (`scripts/perf/detect-input-eval.ts`).** The gate area is cut out of the replay
  clips at the ground-truth moments and every geometry runs on the SAME pixels, 1 ORT thread, `--cpus 1.5`,
  `nice -n 15`, in a throwaway container. Two FP32 references on the strip itself: `ref-fp32-1280` (the
  1280x1280 square the brief names) and `ref-fp32-native` (the strip at scale 1, the upper bound). Recall =
  reference faces >= 60 px (source pixels) matched at IoU >= 0.5. "emb drift" = 1 - cos between the FP32
  ArcFace embedding taken with the candidate's landmarks and with the native reference's landmarks on the
  same frame (the metric PERF used for INT8). Times are the detector only (all runs of a frame summed),
  p50; p95 is omitted for the two runs the load guard paused mid-frame.
  - Scripted entry (2074x432 area = `{0.24,0.30,0.54,0.20}`): 72 frames = 36 persons x 2 moments
    (`firstUsableS + 0.15 s`, face ~62 px, and `+ 1.5 s`, ~90 px); 117 reference faces >= 60 px
    (median 81 px, p5 62 px).
  - NVR entry (3408x456 area = `usable-areas.json`): 110 frames, every 1.5 s of the 18 real passages
    (held-out half; the other 109 frames calibrated the INT8 export). Only 9 faces >= 60 px exist in them
    (median 91 px): real entry passers-by are mostly < 60 px in the 4K picture, so the NVR set measures
    landmark/embedding quality, not recall.
- **Dynamic INT8 export (`det_10g_int8_dyn.onnx`).** `quantize.py --dynamic-hw --keep-heads-fp32 --method
  minmax`, U8S8 per-channel like PERF's shipped INT8, calibrated on 96 tensors = 48 held-out NVR frames x
  {1696x224 auto shape, 640x640}. Input `[1,3,h,w]`; runs at 640x640, 1408x288, 1696x224, 2592x352, 3424x480.
  sha256 `69ae9a3bfd36d4b1c9df55e82bc31902813e83006b9678017b6e3c6725d3e88b`, 4.6 MB, in `/data/models`
  next to PERF's static export (not committed).

### Recommendation

**Ship (c): `PIPELINE_DETECT_INPUT=auto` with the dynamic INT8 detector**
(`PIPELINE_DETECTOR_VARIANT=int8`, `PIPELINE_DETECTOR_MODEL=det_10g_int8_dyn.onnx`, `PIPELINE_ORT_THREADS=1`).

- Same detector cost as today's INT8 square (288-298 vs 277 ms per frame), recall of >= 60 px entry faces
  95% instead of 47% on the scripted strip, landmark error halved and embedding drift p95 0.08 instead of
  0.26-0.45 on the real footage. Every other option that reaches >= 95% costs 2.4-6x more.
- It also helps the exit area (1777x681 -> 1024x384, scale 0.56 instead of 0.36) and any full frame
  (1920x1080 -> 832x480, 0.43 instead of 0.33) at no extra cost, so it can become the pipeline default once
  the dynamic export is the INT8 file the workers load.
- If the CPU budget grows (owner compute decision), `auto:960` at ~650-700 ms buys the last 5% (100% on
  the scripted set) and finer landmarks. `tiles:4` is the fallback that needs no new model file (100%
  recall, best landmarks, 3.9x the detector cost) and works with the static export.
- `auto` with the static `det_10g_int8.onnx` does not start (fail closed, reason in stats): use
  `tiles:<n>` or the FP32 detector there.

## Data and deployment

- **Forward migration:** none.
- **Rollback or compensation:** unset `PIPELINE_DETECT_INPUT` (or `square`) and restart: the pipeline is
  back to the 640 square. `FACE_ORT_LOG_LEVEL` unset restores ORT's default logging. Nothing persists.
- **Backward compatibility:** legacy engine defaults, the `arcface_w600k_r50` tag and all templates are
  unchanged (the detector never affects the tag). Existing `PIPELINE_*` settings keep their meaning; with
  `tiles:<n>` the tile square is `PIPELINE_DETECT_SIZE` (640 for INT8).
- **Data retention/deletion impact:** none.
- **Deployment/restart required:** for anyone who wants it: an env change + restart (no rebuild needed for
  the settings; the code needs a rebuild, `dist/pipelineWorker.cjs` is rebuilt by `npm run build`). Not
  deployed by ENTRY.

## Risks and follow-up

- **Known risks:**
  - The dynamic INT8 export was calibrated on 48 NVR entry frames (two shapes) and measured on 110 held-out
    NVR frames and the 72 scripted frames; PERF's static export used 64 frames of both gates. Before it
    replaces the static file for the EXIT gate, run `detect-input-eval.ts` on the exit clips (the script
    takes any clip + ROI) - expected to hold, since INT8-vs-FP32 at equal geometry cost <= 4 of 117 faces here.
  - `auto` on the NVR strip is scale 0.49 (60 px -> 29 px at SCRFD). The scripted strip is 0.67. Faces at
    exactly the 60 px floor are the ones `auto` still misses (6 of 117 at 62-63 px). If the owner wants the
    floor faces too, `auto:960` (2.4x detector cost) or a taller gate area (more height = more scale at the
    same budget: a 3408x600 area would give 0.65) fixes it without code.
  - ORT's baked output-shape warnings are silenced for the pipeline worker only (`FACE_ORT_LOG_LEVEL=3`);
    other ORT warnings from that worker are silenced with them. Set `FACE_ORT_LOG_LEVEL=2` to see them.
  - Tiling merges with NMS 0.4 plus a 0.6 containment rule; a face straddling a seam at ~50 % visibility
    in both tiles is kept once, but two real faces overlapping > 60 % of the smaller one would also merge
    (unit-tested rule; in practice such faces overlap in the picture too).
  - Not measured at full replay length (see the blocker above): frames/s, loop p50/p95 and CPU with the
    reader and ArcFace in the loop. The detector cost is unchanged at `auto`, so PIPE's rc2 numbers
    (0.9-1.2 frames/s at 4 cores, ArcFace-bound) should carry over; the change is which faces reach ArcFace.
- **Unresolved questions:**
  - Owner/INT: adopt `det_10g_int8_dyn.onnx` as THE INT8 detector file (replace `det_10g_int8.onnx` in
    `/data/models`, one variant, any shape), or keep both and select the dynamic one per gate with
    `PIPELINE_DETECTOR_MODEL`? I recommend replacing after an exit-clip check.
  - Should `auto` become the pipeline default (blank = auto) once the dynamic file is in place? It is the
    better geometry for every area measured, and the fail-closed check protects a static file.
- **Dependencies on other agents/commits:** none for merging (no hotspot touched). Runtime: the model
  volume must carry `det_10g_int8_dyn.onnx` (P2) and compose must pass the two variables (P1).
- **Requested integration action/order:** INT merges `feat/rt-entry` (5 commits, no conflicts with
  `main` @ 89c7df0) after MT/INT re-run the scripted replay with the recommended settings on a quieter host
  (P3). Then the RC settings for a shadow deploy become: `PIPELINE_DETECTOR_VARIANT=int8`,
  `PIPELINE_DETECTOR_MODEL=det_10g_int8_dyn.onnx`, `PIPELINE_DETECT_INPUT=auto`, `PIPELINE_ORT_THREADS=1`.

- **P1 (INT, `docker-compose.yml` / `.env.example`):** pass `PIPELINE_DETECT_INPUT` and
