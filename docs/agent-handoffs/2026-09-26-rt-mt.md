## Legacy baseline (scripted clips, isolated PostgreSQL gateway, 2 cores, watcher gap 3 s, 1 frame, defaults)

Each person's face is >= 60 px and clear for exactly 3 s (40 -> 110 px walk-in); faces are shifted
0/1/2/3 s across cycles so the entry keyframe (every 4 s; legacy decodes keyframes only) falls in the
window 3 times in 4, as with random arrivals. Detector size = code default 640 (the compose file does not
pass `FACE_DETECT_SIZE`, so production uses 640). Run `20260926T195542Z-legacy`.

Reading:
- Every decided person got exactly one log (cooldowns work: no duplicates, no phantom logs, no false
  accepts); the problem is coverage. A look starts every 6 s (exit) / 8 s (entry) against a 3 s usable
  window, and the entry grab alone waits ~3.9 s for a keyframe.
- Entry is also detection-limited: at detector size 640 a 60-110 px face in a 4K frame is mostly not
  found (verify pass: 4/18 samples at 640, 18/18 at 1280), so entry decides ~1 person in 9.
- False rejects are the employee's second view (same-camera cosine ~0.55 before compression): identity
  quality, not timing.
- Variance: an earlier run (v1, same exit clips, entry keyframe-biased) gave exit 61.1% missed,
  p50/p95 3.20/6.45 s; over both runs exit missed 69% (22/72 decided).
- Sensitivity, `FACE_DETECT_SIZE=1280` (v1 clips; exit half valid): exit missed 80.6%, p50/p95 6.60/9.29 s,
  look every 8.2 s, CPU idle 1.08 / busy 1.07 cores. A bigger detector makes each look slower and loses
  more people: the legacy watcher is cadence-limited; the gate-area crop is the lever, not detector size.
- Caveat: pasted stills (no pose change, no motion blur) make recognition easier than on site, so these
  miss rates are a lower bound for legacy; cadence, latency and CPU are representative.

Raw data: `/data/test-clips/results/2026092*-legacy*` (0700); anonymised metrics committed in
`tests/master/results/2026-09-26-legacy-scripted.{json,md}` (+ the two v1 reference runs).

## Production issues found (minimal findings for the owners; no production code changed)

- **F1 SSRF-VIEWER-URL — high.** `GET /api/camera-streams/snapshot?url=` and `GET /api/camera-streams/mjpeg?url=`
  (viewer role) make the gateway's FFmpeg open any `rtsp://host:port` the caller names; the listener in the
  test container received the connection within 4 s. The MJPEG variant has no timeout or concurrency cap, so a
  viewer can also hold unbounded FFmpeg processes. Preconditions: any viewer session. Expected: media routes
  only use configured stream ids; drop the `url` query override (the UI never sends it). Regression: the two
  `[SSRF-VIEWER-URL]` cases in `tests/master/security/security.test.ts`. Owner: INT (`server.ts`).
- **F2 SSRF-STORED / loopback — medium.** Stream create/update and `POST /api/camera-streams/config` (operator)
  accept `127.0.0.1`, `localhost`, `169.254.169.254`, `[::1]`, `0.0.0.0` and any internal host; the scan then
  dials it. Expected: backend allowlist (e.g. `CAMERA_ALLOWED_HOSTS` with the camera/NVR subnets), deny
  loopback/link-local/metadata after DNS resolution, checked on write and on use. The test harness would then
  be allowed via test-environment configuration only. Regression: `[SSRF-LOOPBACK]`, `[SSRF-STORED]`.
- **F3 SSRF-TEST-STREAM — medium.** `POST /api/camera-streams/test-stream` (operator) opens a TCP connection to
  any host:port and reports reachability: an internal port scanner. Expected: same allowlist.
- **F4 SSRF-WEBHOOK — medium (admin only).** Webhook URL has no destination allowlist (the gateway POSTed to the
  test listener); the door-controller `apiUrl` follows the same pattern (not exercised). Expected:
  `WEBHOOK_ALLOWED_HOSTS` / fixed door host, deny internal destinations.
- **F5 CRED-SCAN-DETAILS — high.** `POST /api/camera-streams/scan-rtsp` failure (502) returns `details` = raw
  FFmpeg stderr, which contains `rtsp://<user>:<password>@...` of the configured stream; config APIs redact it,
  this path does not (planted password came back). Same pattern: `POST /api/employees/:id/templates/capture`
  returns `rejected[].detail` from the FFmpeg log. Expected: pass through `redactRtsp()` (exists in
  `src/server/recording.ts`) or drop the field. Regression: "a planted camera password never comes back...".
- **F6 AUDIT — medium.** `GET /api/logs/:id/image` (biometric) is not audited; recording views are only a
  console line. Proposal for DAT/INT: an append-only `biometric_access_audit` table (actor, role, resource,
  id, time) written by image/crop/recording reads; the MT log scan and a future API test will check it.
- **F7 request logger (by code inspection).** `[HTTP GET] ${req.url}` logs query strings; with F1 a URL with
  credentials passed as `?url=` would be logged verbatim. Fixed by F1; consider logging `req.path` only.
- **F8 4K entry detection (functional).** At the default `FACE_DETECT_SIZE` 640 a 60-110 px face in the 4K entry
  frame is mostly not detected (4/18 samples vs 18/18 at 1280). The pipeline's gate-area crop (STR/PERF) must
  feed the detector a region where a 60 px face is >= ~20 px at detector input; the acceptance suite will show it.
- **F9 flaky PostgreSQL case.** strangers "dismiss records immutable adjudication..." failed once in two full
  PG runs under host load (lookup 404 right after creation), never in isolation. Watch in W2 gates.
- **F10 burst rate (STR, contract question for INT).** After an unpaced burst (catch-up after a stall),
  `createStreamReader` hands out up to 21 frames/s (target ~8): the `fps` filter works on stream time, so
  time-compressed input yields time-compressed output and `capturedAtMs` spacing no longer matches the
  scene. No backlog is drained afterwards and `latest()` stays newest-only (both pass). Decide whether
  FrameSource caps hand-out in wall time; if not, MT relaxes that assertion.
