# Agent handoff

## Task

- **Title:** N-gate wave, frontend (plan `docs/plans/2026-09-29-scale-and-accuracy.md`, Part E section 6 and section 11 "Contract").
- **Owner/agent:** ng-ui (frontend).
- **Acceptance criteria:**
  1. Every two-gate UI is a gate list keyed by gate id, never by direction.
  2. The UI works against a new server (`config.gates`, runtimes with `gateId`) and an old one (`entryGate`/`exitGate`, runtimes with `gate: ENTRY|EXIT`). One adapter does this: `src/utils/gates.ts`.
  3. Camera config page: tabs come from the gate list. Admins can:
     - add a gate (`POST /api/gates`);
     - edit its label, direction and door (`PUT /api/gates/:gateId`);
     - disable it with the existing toggle;
     - remove a non-legacy gate (`DELETE /api/gates/:gateId`), after a confirmation that says history is kept.

     Stream, watch, pipeline-mode and ROI calls use the gate id. The overview is a grid of all enabled gates.
  4. Dashboard: per-gate state and video refs are maps keyed by gate id. SSE payloads are routed by `gateId`, with the direction as fallback for old events. There is a "bật tất cả cổng" button.
  5. Engine card and `utils/pipelineMode.ts`: rows and the accuracy section come from the gate list, so the key list is dynamic.
  6. Scanner: the gate is picked from the list.
  7. Logs:
     - the Vào/Ra filter stays, and a gate filter is added (`GET /api/logs?gateId=`);
     - each event shows its gate label (old events: ENTRY → entry, EXIT → exit);
     - the recording badge is per gate.
  8. Enrolment: cameras are grouped by gate label, and the enrol gate is picked from the list.
  9. Door page:
     - the door list comes from `doors[]`, with the single config as fallback door "main";
     - admins can add and edit doors via the existing POST with `doors`;
     - lock controls work per door;
     - tokens are never shown back.
  10. Tests: pure-helper and source-inspection, at least 12 cases.
- **Scope explicitly excluded:**
  - `server.ts`, `src/server/**`, `src/types.ts`, `src/App.tsx`, `auth.ts`;
  - any schema, environment or route change;
  - deleting doors;
  - App-level lock state per door.

## Changes

- **Files changed:** see Ownership.

### The adapter (`src/utils/gates.ts`)

`src/utils/gates.ts` mirrors the id rules of `src/server/gates.ts` without importing it, because that module belongs to the server bundle. A test pins the two together. It provides:

- `gatesOf(config)` returns `GateConfig[]` for either shape. Invalid, duplicate and unknown-direction entries are dropped, and `gateType` is set to the direction.
- `serverHasGates(config)` says whether the server sends the new shape.
- `runtimeGateId(raw)` returns `gateId`, or the gate for the direction an older server sent (`EXIT` → `exit`).
- `eventGateId(log)` matches `gateIdForLegacyRow` and also reads the `scanType` alias.
- `gateIdFromAny`, `gateDisplayLabel` (label > name > legacy label > id), `labelForGateId` (a deleted gate still shows its id), `canDeleteGate` (false for entry and exit), `gateDoorId` (fallback `main`).
- `updateGateInConfig` keeps the `entryGate`/`exitGate` views in step.
- `orderedGateIds`, `suggestGateId` (slug from a Vietnamese label), `validateGateDraft`.
- The `POST`/`PUT`/`DELETE /api/gates` request builders, `interpretGateMutation` (only a 2xx with `success: true` counts as applied; a refusal and a transport failure stay distinct), and `deleteGateConfirmText`.

### The door helpers (`src/utils/doors.ts`)

- `doorsOf(config)` reads `doors[]`, or treats an older server's single config as door `main`. It drops every token field on read and keeps only `hasToken`, taken from `hasApiToken`, `apiTokenSet` or a non-empty `apiToken`.
- `buildDoorSavePayload`: the top level mirrors door `main`; `doors[]` goes only to a server that sent it; `apiToken` is sent only for a door where the admin typed one.
- `buildDoorTestConfig` and `withoutTokens` (used before the config is re-emitted on the client event bus).
- Lock helpers: `buildLockStateUrl`, `buildLockCommandRequest` with `{doorId, source}`, `readLockState`, `interpretLockCommand`.
- `readLockState` never shows door main's state for another door: a state with no `doorId` is read as `main`.

### Engine card and `pipelineMode.ts`

- `GateKey` is now `string`. `GATE_KEYS` is replaced by `LEGACY_GATE_KEYS` and `gateKeysForCard(gates, rows)`.
- `gateKeyOf` now accepts slugs (`"side"` → `"side"`). It was `null` before; the existing test is updated.
- `gateLabel(key, label?)` and the confirm/interpret helpers take an optional label.
- `GatePipelineRow` gains `label`, and its `gate` (the direction) may be null.
- The interpret outcome gains `gateId`. When an older server's answer names only a direction, the gate that was asked for is trusted.
- The card reads `/api/camera-streams/config` on open and on "Đọc lại", for row order and labels. Rows come from the gate list plus any gate the watchers report.
- Each row shows "Vào/Ra · id". The accuracy section matches rows by gate id; old rows match by direction.

### Camera config page

- Tabs:
  - It is an ARIA `tablist`: arrow keys, Home and End move between tabs, with roving `tabIndex`.
  - There is one tab per gate, showing label, direction, stream count and enabled dot, plus "Tổng Quan Tất Cả Cổng" (a grid of every enabled gate with its direction and door).
- "Thêm cổng" (admin):
  - It opens a modal with the label (it auto-suggests the id until the id is edited), the id slug, the Vào/Ra direction and a door select.
  - The door select is filled from `GET /api/door-controller/config` `doors`, with fallback `main`.
  - A refusal stays inside the dialog as an alert. Nothing is added locally.
- "Thông tin cổng" panel (admin):
  - It edits label, direction and door, and saves them through `PUT`.
  - "Xóa cổng" is disabled for entry and exit, and on an older server.
  - Deleting opens an `alertdialog` that says history is kept and ids are not reused.
- Results appear in a polite live region.
- "Lưu Cấu Hình":
  - A server with gates gets `{...globals, gates: [...scalars, no streams]}`.
  - An older server gets `entryGate`/`exitGate` as before.
- The stream fallback (whole-gate POST on a 404 from the thin endpoints) is limited to the two legacy gates. Any other gate gets an explicit error instead.
- The scan sends `gate: <id>` and `scanType: <direction>`.
- Removed: the `localStorage` copy of the camera config, which held camera URLs that may carry credentials. Nothing read that copy.

### Dashboard

- Watchers, pending flags, field errors, interval drafts, alert signatures and scan state are now records keyed by gate id. `setterFor(gateId)` gives each gate a `useState`-style setter.
- Webcam handling:
  - Video and MediaStream refs are maps.
  - One effect diffs the set of gates whose primary stream is CLIENT_UVC and stops or starts per gate.
  - A late `getUserMedia` for a superseded request is stopped at once.
  - Unmount stops every track.
- SSE `gate_watch_state` and `gate_watch_result` payloads are routed with `runtimeGateId`.
- Cards and element ids use the gate id. For legacy gates this gives the same `btn-scannow-entry` etc. as before.
- "Khuôn mặt vừa chụp tại cổng" filters by `eventGateId`.
- The live feed shows the gate label next to VÀO/RA.
- "Mở Cổng Này":
  - It sends `doorId` (the gate's door) and shows the server's answer in a live region.
  - **Fix:** an HTTP refusal used to fall through to the demo simulation when demo persistence was on. Now only a transport failure (status 0) on the static demo build is simulated, and it is labelled.
- "Bật tất cả cổng (trên trang này)" turns on every gate in the local view. It does not save; that was the behaviour before too. The text says so.
- The summary chip now reads "Khóa cửa chính" (App's lock state is door main).

### Scanner, logs and enrolment

- **Scanner:** a `<select>` lists the configured enabled gates, defaulting to the legacy pair. `scanType` is the gate's direction, and `gateId` is sent too (see the proposals below).
- **Logs:**
  - The gate filter is shown only when the server sends `gates`, because an older server would silently ignore it.
  - "Xóa lọc" resets the gate filter too.
  - Each row has the gate label above the direction pill. The caption and recording title use the gate label.
  - The badge comes from `gateHasRecording(recordingGates, eventGateId(log))`.
- **Recordings:** `readRecordingGates` accepts direction keys (old server) and gate-id keys (new server). The id key wins.
- **Enrolment:**
  - The gate select lists every configured gate, marking disabled ones.
  - The camera and template cards are grouped under gate-label headings; unknown cameras come last.
  - The capture request sends `gate: <id>`.

### Door page

- New "Danh Sách Cửa" section. Each door shows:
  - label, id and enabled state;
  - the gates bound to it (read from the camera config);
  - its lock state.
- Admins get Mở and Khóa buttons, plus a refresh, per door. The outcome goes to a live region. A refusal or transport failure is never shown as an opened door.
- Selecting a door makes the existing form edit that door's controller. Id and label are protected from the form.
- "Thêm cửa" (only if the server sent `doors[]`) adds a door locally: disabled, no URL, no token. "Lưu Cấu Hình" sends it.
- Token handling:
  - The token input starts empty, with the placeholder "Đã có token lưu trên máy chủ - để trống để giữ nguyên".
  - A typed value is sent; clearing the field again means keep the stored token.
  - The cURL preview shows `<TOKEN>`.
- Load and save errors are shown, saying what was and was not saved. Save renders the server's returned config.
- The test request adds `doorId`.

### Behaviour, contracts and impact

- **API/event contracts added or changed:** none beyond plan section 11. The proposals below list what the UI assumes where section 11 is silent.
- **Schema/migration changed:** no
- **Environment/configuration changed:** no
- **Security/privacy impact:**
  - No credentials enter browser state. Door tokens are dropped on read and never rendered or put in the cURL preview. The camera config (camera URLs) is no longer written to `localStorage`.
  - Every gate, door and lock mutation goes through `operatorJsonFetch` (CSRF-aware) and renders the server's answer. Nothing is applied optimistically or kept after a refusal.

  - The UI makes no access decision.

## Risks and follow-up

- **Known risks:**
  - **Save sends the whole `gates[]`.** On a server with gates, "Lưu Cấu Hình" sends every gate's scalars, including `watch` and `pipelineMode`. That is the same stale-write exposure entry and exit had before. If the server treats `gates` as a full replacement, a stale page could re-add a gate deleted elsewhere, or drop one added elsewhere. See proposal 3.
  - **App's single lock state.** `App.tsx`, which this task did not own, still keeps one `lockState` and does not filter SSE `lock_state` events by `doorId`. Once doors are real, a lock event for door `kho-b` would overwrite the main lock shown in SmartLockCard and on the dashboard summary. See proposal 12.
  - **Local-only button.** "Bật tất cả cổng (trên trang này)" changes only the local view, as before. It is labelled so.
  - **Source-inspection tests** pin a few shapes in the changed components:
    - `runtimeGateId(payload)`;
    - `canDeleteGate(currentGateKey)`;
    - `gateKeysForCard(gates, rows).map(renderRow)`;
    - `buildDoorSavePayload(doors, tokenDrafts, multiDoor)`;
    - three `operatorJsonFetch<unknown>(url, init)` calls in the config page.

    Refactors that change these must update `tests/nGatesUi.test.ts`.
- **Unresolved questions / what the backend must provide beyond the contract text:**
  1. **`/api/gates` responses.**
     - Success: `{ success: true, gate, config }`, with `config` the full `CameraStreamsConfig` including `gates`. Without `config` the UI re-reads it.
     - Refusals: `{ success: false, error, code? }` with 400 (validation), 403, 404 (unknown gate), or 409 (duplicate or reused id, or deleting entry/exit).
     - `POST` body: `{ id, label, direction, doorId? }`. `PUT` body: a partial `{ label?, direction?, doorId?, enabled? }`.
  2. **Gate ids in query and body parameters.** These routes must accept a gate id: `GET /api/camera-streams/snapshot?gate=<id>&stream=`, `POST /api/camera-streams/scan-rtsp { gate: <id>, stream?, scanType, frames }`, and `POST /api/employees/:id/templates/capture { gate: <id>, stream? }`. Section 11 names only the `/:gateId/...` path routes.
  3. **`POST /api/camera-streams/config` with `gates` should patch by id.** In particular:
     - a gate without `streams` keeps its stored streams, as entryGate/exitGate do today;
     - a gate missing from the array is not deleted (only `DELETE` deletes);
     - an unknown id is refused or ignored, never created.
  4. **`POST /api/recognize-face` with `gateId`.** The scanner and the dashboard webcam path now send `gateId` next to `scanType`. Please validate it against the configured gates and use it to attribute the event and pick the gate's door. It must never widen access. An older server ignores it.
  5. **`gateId` on the stats and CSV routes.** `/api/logs/stats` and `/api/logs/export.csv` should honour `gateId`. The UI sends it on all three log routes, through the shared `logFilterParams`. Otherwise the totals, chart and CSV ignore the gate filter while the table applies it.
  6. **`GET /api/recordings/config`** `gates` should be keyed by gate id (`{ "entry": true, "exit": true, "kho-b": false }`). Direction keys are still read.
  7. **Lock state route.** Section 11 says `GET /api/lock/state?doorId=`, but the existing route is `/api/lock/status`. Please confirm the name.
     - The response must carry `doorId`, either as a SmartLockState or as `{ success, lockState }`. The UI will not show a state without `doorId` for any door other than `main`.
     - The UI falls back from a 404 to `/api/lock/status` only for `main`.
  8. **Lock commands.** `POST /api/lock/unlock|lock { doorId }` should answer `{ success, message, lockState }`, with `lockState.doorId`. An unknown `doorId` must get 400, not a fallback to `main`.
  9. **Door config tokens.** On this base, `GET /api/door-controller/config` returns the raw `apiToken` to admins. Please mask it and add `hasApiToken: boolean`, per door too.
     - On `POST`, a door entry without `apiToken` keeps the stored token, and `""` clears it.
     - The `POST` response `config` should also be masked. The UI strips tokens either way.
  10. **Door test.** `POST /api/door-controller/test { doorId, testConfig }` should test that door's controller. A `testConfig` without `apiToken` uses that door's stored token.
  11. **SSE and watch payloads.** `gate_watch_state`, `gate_watch_result`, the `pipeline-mode` answer and `/api/camera-streams/watch` entries should carry `gateId` and `gateLabel`. Every configured gate should have a runtime, including disabled ones.
  12. **App lock state (follow-up, frontend or INT).** `App.tsx` should keep lock state per door, or at least ignore `lock_state` events whose `doorId` is not `main`.
- **Proposed hotspot changes (not made):**
  - `src/types.ts` (INT): `DoorAuthHeaderType` should include `"NONE"`. The presets and select already send it, and the door page casts for that comparison. A typecheck caught it once the form's `config` type changed.
  - `src/types.ts` (INT): add `hasApiToken?: boolean` to `DoorControllerConfig`, which `DoorConfig` inherits.
  - `src/server/auth.ts` (INT): the stream, watch and pipeline-mode rules still match only `(entry|exit)`; they need generalising to the gate-id slug. Section 11 already lists this.
- **Dependencies on other agents/commits:** the INT routes (`/api/gates`, gate ids on the camera-stream routes, `doors[]`, `lock/state`, `gateId` on logs and SSE) and the data-migrations `db.ts` work (`access_logs.gateId`, `door_lock_states`).
