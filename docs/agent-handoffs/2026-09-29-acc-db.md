## Changes

- **Files changed:** `src/server/db.ts`, `init-db.sql`, three new test files, two predecessor tests (exact
  column/index lists), this handoff.
- **Behavior changed:**
  - **Shadow results** (`SQLiteStorage implements ShadowResultStore`). Same single-authority rule as stranger faces:
    exactly ONE store holds them - PostgreSQL when it is the active authority and `pipeline_shadow_results` exists,
    else native SQLite, else JSON. While PostgreSQL is configured but connecting, or if its DDL failed (logged),
    `saveShadowResult` returns `false` and reads are empty / `[]` / `0`. No local mirror.
  - `saveShadowResult`: awaited `INSERT ... ON CONFLICT (id) DO NOTHING` (SQLite: same; JSON: temp + rename before
    the in-memory swap). Replay by id is a no-op (first write wins); concurrent duplicates all return `true`, one row.
    Validation (`normalizeShadowResult`, exported) refuses (`false`, logged) a malformed required field: id
    (`^[A-Za-z0-9][A-Za-z0-9._:-]{0,63}$`), gate (same regex, <= 64), trackId (<= 64), outcome enum, employeeId
    required for `employee` outcomes and, when present, printable ASCII <= 64 (also runnerUpEmployeeId,
    legacyEmployeeId), legacyLogId (<= 64), legacyStatus enum, basis (1..128 printable), framesSeen/Used (int
    0..2^31-1), firstSeenAt / decidedAt (ISO, normalised to UTC ms), agreement enum. Dropped to NULL, never fatal:
    non-finite / |v| > 1e6 fusedCosine, margin, runnerUpCosine; over-long fusionBasis; unparseable firstUsableAt.
    `meanCheckRefused` is stored as given (`true` / `false` / NULL) and read back the same (NULL = absent).
  - `getShadowResultsPage`: `(decidedAt DESC, id DESC)` keyset, strict `<` cursor, limit clamped 1..100, filters
    `gate` (exact), `agreement` (exact; an unknown value returns an empty page), `sinceIso` (`decidedAt >=`,
    inclusive; unparseable -> `RangeError`). PostgreSQL `id` and `decidedAt` are `COLLATE "C"` so ordering is
    bytewise exactly as SQLite/JSON.
  - `summarizeShadowResults(sinceIso)`: one row per gate with results at/after `since` (inclusive), gates in bytewise
    order, `since` echoed normalised. Counts aggregated in SQL (PG `FILTER`, SQLite `sum(cond)`), or in JS for JSON;
    `decisionLatencyP50Ms` computed identically for all stores (`medianMs`, exported): sorted
    `Date.parse(decidedAt) - Date.parse(firstUsableAt)` over rows with `outcome = 'employee'` and a `firstUsableAt`,
    middle value or mean of the two middle values, rounded to whole ms; `null` when there is no sample.
    Unparseable since -> `RangeError`.
  - `purgeShadowResults(cutoffIso)`: `DELETE ... WHERE decidedAt < cutoff` (strict), returns rows deleted; idempotent;
    unparseable cutoff -> `RangeError`. Nothing biometric lives in the table, so a plain delete (no tombstone).
  - **Observations.** `normalizeStrangerFace`: `employeeId` (printable ASCII <= 64, `EMPLOYEE_ID_RE`) with BOTH
    `matchCosine` and `matchMargin` finite -> stored; `employeeId` present without both scores, or unstorable
    -> the batch is refused (`false`, errors `matchScores` / `employeeId`); a face without `employeeId` never stores
    match scores (a stray `matchCosine` on a stranger is dropped). The `(logId, faceIndex)` slot rule is unchanged:
    a GRANTED frame's recognised face and its strangers are distinct slots of the same event.
  - `getStrangerFacesPage` adds `AND employeeId IS NULL` (PG/SQLite) / `!face.employeeId` (JSON): recognised faces
    never reach stranger grouping. `getStrangerFacesByIds`, `getStrangerFacesByLogIds`, `getStrangerFaceCrop`,
    `purgeStrangerFaces`, `clearAccessLogs` unchanged and apply to observations. A purged observation keeps
    `employeeId`, `matchCosine`, `matchMargin` on its tombstone (provenance), never embedding/crop.
  - `getRecognisedFaceObservations(sinceIso, employeeId?, limit?)`: `employeeId IS NOT NULL AND purgedAt IS NULL AND
    capturedAt >= since`, optional exact employee filter, `(capturedAt DESC, id DESC)`, embedding included, crop
    never, limit clamped 1..2000 (default = 2000). Unparseable since -> `RangeError`; an `employeeId` the column could
    not hold -> `[]`. Served by the new partial index `idx_stranger_faces_recognised ("employeeId", "capturedAt"
    DESC, id DESC) WHERE "employeeId" IS NOT NULL AND "purgedAt" IS NULL`.
  - **Templates.** `FaceTemplateSource = FaceTemplate["source"]` (single definition in `src/types.ts`; see
    "Requested integration action" 1). No store validates or constrains `source` (VARCHAR(32) / TEXT, no CHECK), so
    `"adaptation"` templates round-trip on every store already; `deleteFaceTemplate` is by id. New
    `countFaceTemplatesByEmployeeAndStream(): Promise<FaceTemplateCount[]>` = `{ employeeId, streamId: string|null,
    source, count }` over the in-memory gallery (exactly what matching uses; every write updates it synchronously),
    sorted by employeeId, streamId (null first), source.
  - **Fix (pre-existing race, found by the PostgreSQL test):** `saveFaceTemplate` / `deleteFaceTemplate` issued their
    PostgreSQL statements unordered on the pool, so a delete could overtake the insert of the same id and the
    template came back at the next restart (a `saveFaceTemplate` immediately followed by `deleteFaceTemplate` of the
    same id reproduced it). PostgreSQL template writes now run in issue order through one promise chain; errors are
    logged (the delete used to swallow them). New `settleFaceTemplateWrites(): Promise<void>` resolves once every
    template write issued so far has finished - the adaptation job should await it before reporting success.
    Callers' synchronous signatures are unchanged.
- **API/event contracts added or changed:** none at HTTP level. Store contracts implemented as written; stricter-than-
  written behaviours: `RangeError` on unparseable `sinceIso` / cutoff; `false` for malformed records or PostgreSQL not
  ready; observations refused without both scores. Additive: `normalizeShadowResult`, `medianMs`,
  `FaceTemplateSource`, `FaceTemplateCount`, `countFaceTemplatesByEmployeeAndStream`, `settleFaceTemplateWrites`.
- **Schema/migration changed:** yes (additive), see Data and deployment.
- **Environment/configuration changed:** none (retention days are read by INT's scheduler from the contracts:
  `SHADOW_RESULT_RETENTION_DAYS`, `FACE_STRANGER_FACE_RETENTION_DAYS`).
- **Security/privacy impact:** `pipeline_shadow_results` holds ids, scores, bases and times only - no image, no
  embedding, no BLOB/BYTEA column (asserted). Observation rows are biometric like stranger faces (same store, same
  retention purge, same tombstone rule); they add WHO the door engine granted, which is an access fact already in
  `access_logs`. `getRecognisedFaceObservations` returns embeddings server-side; INT must never put them in an API
  response. No second copy of either table while PostgreSQL is active.

## Data and deployment

- **Forward migration:** automatic at startup, additive, no backfill.
  - PostgreSQL: `PG_STRANGER_FACES_DDL` (own statement, after the main batch) now also runs `ALTER TABLE stranger_faces
    ADD COLUMN IF NOT EXISTS "employeeId" VARCHAR(64) / "matchCosine" REAL / "matchMargin" REAL` (nullable, no
    default: catalog-only, no rewrite) and `CREATE INDEX IF NOT EXISTS idx_stranger_faces_recognised ... WHERE ...`
    (builds over existing rows; the partial predicate matches none of them, so it is tiny). `PG_SHADOW_RESULTS_DDL`
    runs as its own statement with its own `pgShadowResultsReady` flag, so a failure there cannot roll back anything
    else (logged; shadow writes then refused, everything else unchanged). `init-db.sql` carries the same DDL for new
    databases.
  - SQLite: `CREATE TABLE IF NOT EXISTS` with the new columns last; `ALTER TABLE stranger_faces ADD COLUMN ...` x3
    (duplicate-column error = already done) so a migrated database has the same column order as a fresh one; then
    the recognised index and the shadow table.
  - JSON: new optional key `pipeline_shadow_results`; faces without `employeeId` read as strangers.
- **Rollback or compensation:**
  - To the previous image (per-face release): no DDL needed (tested on PG and SQLite). Old code never names the new
    columns (its 20-column INSERT gets NULLs, its explicit SELECT ignores them) and never reads
    `pipeline_shadow_results`. CAUTION: old code's grouping page has no `employeeId IS NULL` filter, so observation
    rows written by the new release would appear as strangers until their 14-day purge. Compensation before/with a
    rollback (biometric hygiene, not correctness of the door): `UPDATE stranger_faces SET crop = NULL, embedding =
    NULL, "purgedAt" = now()::text WHERE "employeeId" IS NOT NULL AND "purgedAt" IS NULL;` (or `DELETE ... WHERE
    "employeeId" IS NOT NULL`). Adaptation templates need no schema change to survive; to withdraw them: `DELETE FROM
    face_templates WHERE source = 'adaptation'` (they are derived data, re-derivable by the job).
  - Full schema removal (optional): `DROP TABLE pipeline_shadow_results; DROP INDEX idx_stranger_faces_recognised;
    ALTER TABLE stranger_faces DROP COLUMN "employeeId", DROP COLUMN "matchCosine", DROP COLUMN "matchMargin";`
    Tested: stranger faces and adjudications survive; observations become stranger faces (purge them first, above);
    a restart re-applies the migration idempotently.
- **Backward compatibility:** `StrangerFaceRecord` gains optional fields only; every existing caller behaves as
  before (old rows read them absent). `getStrangerFacesPage` returns a subset of what it did (no observations),
  which is the contract. `FaceTemplateRecord.source` type is unchanged until INT widens `FaceTemplate.source`.
- **Data retention/deletion impact:** shadow results: INT schedules `purgeShadowResults(now - days)` with
  `shadowResultRetentionDays()` (owner: 30 days; 0 = disabled); no biometric data; no tombstone. Observations: same
  clock and same job as stranger faces (14 days), tombstone keeps employeeId + scores (no biometric bytes)
  indefinitely, like stranger tombstones; deleted with their access event (admin clear, cascade). Adaptation
  templates: kept until an operator deletes them or the job evicts them (plan: 5 per camera per employee); no
  retention clock (they are the gallery). Legal hold: out of scope. Orphans: shadow results deliberately have no FK
  (`legacyLogId` may dangle after an admin clear of the history - it is a reference, not a join; the row is purged by
  retention); observations are FK-bound like stranger faces.
- **Deployment/restart required:** yes, as part of the integrated accuracy release (migration runs at startup). Not
  deployed.

## Risks and follow-up

- **Known risks:**
  - `getStrangerFacesPage` still walks `idx_stranger_faces_captured` and filters `employeeId IS NULL` per row: on a
    gate where recognised faces outnumber strangers, a page reads more index entries than it returns. The grouping
    job walks the whole unpurged set anyway (bounded by the 14-day purge), so the total work is unchanged; if a
    partial index on `employeeId IS NULL` is wanted later it is one `CREATE INDEX IF NOT EXISTS`.
  - `countFaceTemplatesByEmployeeAndStream` counts the in-memory gallery. Before PostgreSQL hydration completes at
    startup it reflects the local store (existing `getFaceTemplates()` behaviour).
  - `saveFaceTemplate` / `deleteFaceTemplate` still return before PostgreSQL has the row (unchanged signatures); the
    order is now guaranteed and `settleFaceTemplateWrites()` gives the awaitable. A PostgreSQL failure is logged, not
    surfaced to the caller (pre-existing).
  - Shadow results and observations written while running on the local fallback are not visible once PostgreSQL is
    back (same class as access logs written during a fallback; stranded observations are purged by the existing
    local-purge path).
- **Unresolved questions:** default `limit` of `getRecognisedFaceObservations` when omitted is the cap (2000); if the
  adaptation job wants smaller batches it passes a limit.
- **Dependencies on other agents/commits:** INT must widen `FaceTemplate.source` (below) before writing
  `"adaptation"` templates without a cast.
- **Requested integration action/order (INT - proposals only, exact changes):**
  1. `src/types.ts` line ~493, `FaceTemplate.source`: `"enrollment" | "merge" | "manual" | "auto" | "adaptation"`.
     This is the ONLY definition; `db.ts` derives `FaceTemplateSource` from it. `server.ts` ~1983
     (`enrollTemplateFromImage` opts) and ~6528 / ~7563 unions: add `"adaptation"` where the adaptation job calls
     them, or call `db.saveFaceTemplate` directly.
  2. Shadow writer (`reportPipelineResult`, server.ts ~5789): build a `ShadowResultRecord` (`newShadowResultId()`,
     `classifyShadowAgreement(...)` against the nearest access log on the gate within `SHADOW_MATCH_WINDOW_MS`), then
     `await db.saveShadowResult(record)`; on `false` log and continue (the SSE broadcast is unaffected).
  3. Routes: `GET /api/pipeline/shadow-summary?hours=24` -> validate `hours` (int 1..720), `since = new Date(Date.now()
     - hours*3600e3).toISOString()`, `db.summarizeShadowResults(since)`; `GET /api/pipeline/shadow-results?gate=&
     agreement=&cursor=&limit=` -> validate `agreement` against the five values (400), `cursor` as `<decidedAt>|<id>`
     or JSON, `limit` int, `db.getShadowResultsPage(cursor, limit, { gate, agreement, sinceIso })`; catch `RangeError`
     -> 400. Responses carry the records as-is (no embeddings exist there).
  4. Retention: daily `db.purgeShadowResults(new Date(Date.now() - shadowResultRetentionDays()*86_400_000)
     .toISOString())` when days > 0, next to the existing stranger-face purge.
  5. Observation writer (`applyRecognitionOutcome` GRANTED path): for the recognised face of the frame push a
     `StrangerFaceRecord` with `employeeId`, `matchCosine` (fused cosine), `matchMargin` into the same
     `saveStrangerFaces` batch as the frame's strangers, with a distinct `faceIndex`. Never set `employeeId` from a
     stranger merge (plan C3: "never from stranger merges").
  6. Adaptation job: `db.getRecognisedFaceObservations(since, undefined, 2000)` (records -> `RecognisedFaceObservation`
     needs `streamId`, `gate`, `quality`, `embedding`; skip rows without `streamId`/`embedding`), existing =
     `db.getFaceTemplates()`; `planAdaptation(...)`; for each item `db.deleteFaceTemplate(evictTemplateId)` (if any)
     then `db.saveFaceTemplate({ ..., source: "adaptation", streamId, sourceLogId: observation.logId })`; then `await
     db.settleFaceTemplateWrites()` before reporting. Audit line per template (plan C3). Coverage:
     `db.countFaceTemplatesByEmployeeAndStream()` feeds `templateCoverage`/`GET /api/employees/:id/templates`.
  7. Strip `embedding` from every face record in API responses (unchanged rule).
