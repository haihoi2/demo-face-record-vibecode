# Agent handoff: ng-pipe (N-gate wave, pipeline)

## Task

- **Title:** The real-time pipeline's `Gate` becomes the gate id (plan `docs/plans/2026-09-29-scale-and-accuracy.md` section 11, "Pipeline").
- **Owner/agent:** pipeline agent (ng-pipe). Integrator: Hermes/INT.
- **Acceptance criteria:**
  - `Gate = string` (a gate id). It is validated with `isGateId` at every boundary that accepts one: GatePipeline construction, the worker `init` message, and the StreamReader, FaceTracker and TrackDecider/GateTrackSession constructors.
  - The ENTRY/EXIT coercions are removed. An invalid or unknown gate id is refused and never coerced.
  - Track-id prefixes come from the gate id: `E`/`X` stay for `entry`/`exit`, and other ids get the first letter plus a 4-char hash.
  - The worker thread name is `pipeline-<gate id>`.
  - `pipelineModeFromEnv` reads `PIPELINE_MODE_<gateEnvSuffix(id)>`.
  - Tests cover: a third gate end to end, invalid id refused, env mode per gate id, and track-id prefixes for legacy and new gates.
  - Own files typecheck clean. Unit and build pass.
- **Scope explicitly excluded:** `server.ts` (INT), `src/types.ts`, `src/server/gates.ts`, `db.ts`, `scripts/**`, frontend. A `direction` field was NOT added to the pipeline: nothing inside it uses a direction. Logs, worker names and stream ids use the gate id, which is readable. Direction stays with the server's gate config.

## Changes

- **Files changed:**
  - `src/server/pipeline/contracts.ts`: `export type Gate = string;` (documented as a gate id).
  - `src/server/pipeline/gateId.ts` (new): `assertGateId(value, what)` throws a `TypeError` naming the boundary, with the bad value truncated to 40 chars. `trackIdPrefix(gateId)` returns the prefix. `isGateId` is re-exported.
  - `src/server/pipeline/pipelineCore.ts`:
    - No default gate.
    - An `init` with an invalid gate is refused. The worker posts `error` "init refused: invalid gate id …", sets `contextOk=false` and `contextReason` "pipeline worker: init refused (invalid gate id)", never builds a session, and answers every frame with `processed:false`.
    - A context that arrived before `init` is applied once the gate is known.
    - `idPrefix = trackIdPrefix(gate)`.
  - `src/server/pipeline/gatePipeline.ts`:
    - The constructor throws on an invalid gate id, or when `source.gate !== gate`.
    - Worker results whose `outcome.gate` is another gate are dropped and counted as errors ("worker result for another gate dropped").
    - New export `pipelineWorkerName(gate)` returns `pipeline-<id>`.
  - `src/server/pipeline/streamReader.ts`: the constructor throws on an invalid gate id, before any spawn. The "not EXIT becomes ENTRY" coercion is removed in both places. The default `streamId` is the gate id (was `gate.toLowerCase()`).
  - `src/server/pipeline/tracker.ts`: refuses any non-gate-id (was: only ENTRY/EXIT accepted). The default `idPrefix` is `${trackIdPrefix(gate)}-${clock base36}`.
  - `src/server/pipeline/trackDecision.ts`: `TrackDecider` refuses an invalid gate id, and so does `GateTrackSession`.
  - `src/server/pipeline/mode.ts`: `pipelineModeFromEnv(gateId)` reads `PIPELINE_MODE_${gateEnvSuffix(gateId)}`. A value that is not a gate id (e.g. `"ENTRY"`) always gives `legacy`.
  - `src/server/pipeline/pipelineProtocol.ts`: doc only. `InitMessage.gate` is a gate id. The wire shape is unchanged.
  - Tests:
    - Existing pipeline tests now use the ids `"entry"`/`"exit"`: `tests/{tracker,trackDecision,gatePipeline,pipelineWorker,pipelineHost,pipelineMode,pipelineRecognizer,streamReader,faceCrop}.test.ts` and `tests/master/contract/{tracker,frameSource}.test.ts`.
    - New file: `tests/pipelineGateId.test.ts`.
    - New cases in tracker, trackDecision, gatePipeline, pipelineWorker (PipelineCore), pipelineHost, pipelineMode and streamReader.
- **Behavior changed:**
  - Gate values inside the pipeline are gate ids. Frames, SourceState, TrackOutcome, ShadowResult and the worker `init` carry `"entry"`/`"exit"`/`"side-door"` instead of `"ENTRY"`/`"EXIT"`.
  - Track ids are unchanged for the legacy gates (`E-1`, `X-1`, …). For a new gate they look like `S0k3f-1`: the first letter plus 4 base-36 chars of an FNV-1a hash of the id. The prefix is stable across restarts and distinct from `E`/`X`. A collision between two of at most 16 gates is under 1e-4, and the outcome carries the gate id as well.
  - Worker thread names are unchanged for the legacy gates (`pipeline-entry`, `pipeline-exit`).
- **API/event contracts added or changed:** pipeline-internal types only. Once INT passes ids, the SSE `pipeline_shadow_result` payload and `ShadowResultRecord.gate` will carry the gate id. This matches the contract: "Shadow results: `gate` holds the gate id from now on".
- **Schema/migration changed:** none.
- **Environment/configuration changed:** `PIPELINE_MODE_<SUFFIX>` per gate id via `gateEnvSuffix`. `PIPELINE_MODE_ENTRY` and `PIPELINE_MODE_EXIT` keep working for the legacy gates. New gates use e.g. `PIPELINE_MODE_SIDE_DOOR`.
- **Security/privacy impact:**
  - Fail closed is stronger: a mislabelled gate can no longer be decided as the entry gate.
  - Results of another gate never leave a GatePipeline.
  - Error messages carry at most 40 chars of the refused value and never a URL (a test checks that the stream-reader error does not contain the RTSP URL).

## INT call-site to-do (server.ts; not edited here)

The three compile errors are only part of the job. Passing the old directions also breaks at runtime: `createStreamReader` and `new GatePipeline` throw, and `pipelineModeFromEnv("ENTRY")` silently returns `legacy`. Every call site must therefore pass a gate id:

1. **`pipelineModeFor(gate: "ENTRY" | "EXIT")`** (~5404). Change it to `pipelineModeFor(gateId: string)`. Read the configured mode from the gate config found by id (`gates.find(g => g.id === gateId)?.pipelineMode`, not `entryGate`/`exitGate`). Call `pipelineModeFromEnv(gateId)`. This fixes all three TS errors: 5769 `desiredPipeline`, 5833 the start log in `startGatePipeline`, and 5895 `reportPipelineResult`. `gateWatchRuntime` must pass `state.gateId` (or whatever the watcher state's id field becomes), not `state.gate`.
2. **`gatePipelines: Record<Gate, GatePipelineSlot>`** (~5761) with literal `ENTRY`/`EXIT` keys. Make it a `Map<string, GatePipelineSlot>` keyed by gate id, with slots created and removed as gates are configured. A removed gate's pipeline must be `stop()`ped and its slot deleted.
3. **`pipelineErrorLog: Record<Gate, …>`** (~5715) with literal keys. Same treatment: a `Map` keyed by gate id, created lazily in `logPipelineError(gateId, …)`.
4. **`syncPipelines()`** (~5844): `for (const gate of ["ENTRY", "EXIT"] as const)` must loop over the configured gate ids (`cameraStreamsConfig.gates.map(g => g.id)`), and also stop the slots of gates that no longer exist.
5. **`desiredPipeline(gate)`** (~5768): use `resolveGateStream(gateId)` directly. Drop the `gate === "EXIT" ? "exit" : "entry"` mapping, which is the coercion the contract forbids. An unknown id must return `null`.
6. **`startGatePipeline(gate, want)`** (~5780): pass the gate id as `createStreamReader({ gate: gateId, … })` and `new GatePipeline({ gate: gateId, source, … })`. Both now THROW `TypeError` on `"ENTRY"`/`"EXIT"`, which the existing try/catch would log as "Không khởi động được" and run nothing. GatePipeline also throws if `source.gate !== gate`, so pass the same id to both. Log labels `[Pipeline ${gate}]` may use the id or the gate label.
7. **`reportPipelineResult(gate, r)`** / **`persistShadowResult(gate, r)`** (~5889/5935): `gate` and `r.shadow.gate`/`r.outcome.gate` are now the gate id. `ShadowResultRecord.gate` is already `string`, so it compiles, and that matches the contract (shadow results store the gate id; db reads old ENTRY/EXIT rows as entry/exit).
8. **`nearestLegacyEvent(gate, …)`** (~5912) — SILENT BUG if left as is: it compares `log.type !== gate`, which is the access-log DIRECTION against a gate id. It still compiles but would never match, so every shadow result would lose its door-engine pairing (`agreement` becomes "no legacy event"). Change it to `gateIdForLegacyRow(log) !== gateId`. Once access logs carry `gateId`, this works for old rows (derived from `type`) and new rows alike.
9. **`pipelineRuntime(gate: "ENTRY" | "EXIT")`** (~5978): becomes `pipelineRuntime(gateId: string)`, reading the Map slot (return `{}` for a gate without a slot). `const { gate: _g, ...state } = p.sourceState()` stays as is.
10. **`logPipelineStats(gate, pipeline)`** (~5864): key the slot by gate id.
11. **Imports:** `import type { Gate, PipelineMode }` from contracts keeps working (`Gate` is `string`). No pipeline function signature changed except the parameter's meaning (gate id instead of direction). New optional export `pipelineWorkerName` is not needed by the server.
12. **SSE / UI note (frontend):** the `pipeline_shadow_result` event's `gate` becomes the gate id. `src/utils/accuracyUi.ts` already tolerates "ENTRY/entry" through `gateKeyOf`, but anything that filters on `"ENTRY"`/`"EXIT"` must use ids.

**Outside my ownership, proposed:** `scripts/pipeline/measure-stream.ts:71` still does `arg("gate") === "EXIT" ? "EXIT" : "ENTRY"`. It compiles, but `createStreamReader` now refuses those values. Proposed fix (owner: INT/build-release): `const gate = (arg("gate") || "entry").toLowerCase(); if (!isGateId(gate)) throw new Error("--gate must be a gate id")`, importing `isGateId` from `src/server/gates`, and update the usage line (`--gate entry`).
