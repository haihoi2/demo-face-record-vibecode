# Agent handoff - P3b storage: app_settings

## Task

- **Title:** P3b contract section 1 "Storage": generic `app_settings` key/value store in PostgreSQL, native SQLite and the JSON fallback (`docs/plans/2026-10-07-p3b-contract.md`, untracked in the main checkout).
- **Owner/agent:** data-migrations agent (single writer of `src/server/db.ts` this wave). Integration owner: Hermes.
- **Acceptance criteria:**
  - `export interface AppSettingRecord<T = unknown> { key; value: T; updatedAt; updatedBy }`.
  - `db.getAppSetting<T>(key)` is SYNC, served from an in-memory cache, and returns deep copies. It returns undefined for a malformed key or a missing document.
  - `db.saveAppSetting<T>(key, value, actor): Promise<boolean>` writes durably and only then updates the cache. It returns false on store failure, malformed key, or a value over 64 KB / not JSON-serialisable.
  - Keys must match `^[a-z][a-z0-9_]{1,63}$`.
  - On PostgreSQL, the table is created in the normal migration (`CREATE TABLE IF NOT EXISTS`) and the cache is hydrated before the first `db.onSync` callback.
  - SQLite and JSON have the same semantics.
  - Rollback is `DROP TABLE app_settings`.
  - Tests: unit (SQLite and JSON), PostgreSQL persistence (throwaway database only), restart read-back.
- **Scope explicitly excluded:** routes, `server.ts`, `src/types.ts`, the UI, and value validation (the server owns the document shapes).

## Changes

- **Files changed:** `src/server/db.ts` (+~280 lines), plus 3 new test files and this handoff.
- **Behavior changed:** none for existing tables. A new single-authority settings store is added:
  - The active store is PostgreSQL when it is active and `app_settings` has been migrated and hydrated. Otherwise it is native SQLite, or else the JSON file. This uses the same `singleStoreMode` rule as `login_events` and `stranger_faces`.
  - While PostgreSQL is configured but not usable (connecting, or the table migration/hydration failed), reads return undefined and writes return false. Nothing is parked in a local store that the gateway stops reading once it connects.
  - Every write goes through one FIFO queue, so the cache always matches the order in which the store applied the writes. Twenty concurrent saves of one key end on the last call, both in the cache and in the database.
  - Values are frozen to canonical JSON at call time: members set to `undefined` are dropped and a `Date` becomes an ISO string. Neither the caller's later mutations nor mutations of a returned copy reach the cache.
  - The actor is stored trimmed.
  - Strings containing NUL are refused in every store because PostgreSQL JSONB cannot hold them.
  - Rows that fail to parse are skipped and their key is logged. Values are never logged.
- **API/event contracts added or changed:** new `src/server/db.ts` exports:

  ```ts
  export interface AppSettingRecord<T = unknown> { key: string; value: T; updatedAt: string; updatedBy: string }
  export const APP_SETTING_KEY_PATTERN: RegExp;   // /^[a-z][a-z0-9_]{1,63}$/
  export const APP_SETTING_MAX_BYTES: number;     // 65536 (UTF-8 bytes of JSON.stringify(value))
  export type AppSettingUpdateResult<T = unknown> =
    | { status: "saved"; record: AppSettingRecord<T> }
    | { status: "unchanged"; record: AppSettingRecord<T> | undefined }
    | { status: "failed" };

  db.getAppSetting<T = unknown>(key: string): AppSettingRecord<T> | undefined
  db.saveAppSetting<T>(key: string, value: T, actor: string): Promise<boolean>          // never rejects
  db.updateAppSetting<T>(key: string,
    mutate: (current: AppSettingRecord<T> | undefined) => T | undefined,
    actor: string): Promise<AppSettingUpdateResult<T>>
  ```

  `updateAppSetting` is an additive helper beyond the contract (see Risks). No HTTP contract changes.
- **Schema/migration changed:** new table, created additively in all three stores:
  - PostgreSQL: `app_settings (key VARCHAR(64) PRIMARY KEY CHECK (key ~ '^[a-z][a-z0-9_]{1,63}$'), value JSONB NOT NULL, "updatedAt" VARCHAR(64) NOT NULL, "updatedBy" VARCHAR(255) NOT NULL)`.
  - SQLite: the same columns as TEXT, with an equivalent CHECK (built from GLOB and length).
  - JSON: `app_settings: Record<key, AppSettingRecord>`.
- **Environment/configuration changed:** none.
- **Security/privacy impact:**
  - The `notification_channels` value will hold credential-bearing webhook URLs. The db layer never logs values (tests assert that a secret marker never appears in the logs) and never returns them through any route. Masking is the server's job (`urlMasked`).
  - As with the existing `webhook_config`, the URLs are stored in plaintext in PostgreSQL, SQLite and `data/smartface_data.json`.
  - The actor is limited to 255 characters and must be non-empty. The store keeps only the last writer and time. For a full change history, the server should keep its own audit entries.

- **Covered by the tests:**
  - The shared scenario runs in all three stores.
  - Malformed keys, including `constructor`, `tostring` and `__proto__`.
  - Values that are undefined, a function, circular, BigInt, or contain NUL in a value or key.
  - The 64 KB boundary, counted in UTF-8 bytes.
  - Empty, blank, over-long and non-string actors.
  - The cache does not change before the write is durable (PostgreSQL write delayed by 150 ms).
  - Deep copies in both directions.
  - Partial failure: an injected store failure returns false, the cache is unchanged, and a retry succeeds. On PostgreSQL the injected error has code 57P01, on SQLite the error is "database is locked", and on JSON the write path is unwritable.
  - Duplicate submissions, 20 concurrent overwrites (applied in call order), and 12 concurrent read-modify-writes with no lost update.
  - A `mutate` exception rejects and writes nothing, and the queue survives errors.
  - Restart read-back.
  - Hydration is checked synchronously inside the first `onSync` callback.
  - Old JSON store without `app_settings`: existing data is preserved.
  - Malformed stored rows are skipped and their key is logged, never the value.
  - While PostgreSQL is connecting: reads return undefined, writes return false, and the local store is untouched.
  - Stranded local values (written during a fallback period) are not served or copied. Their keys are reported and their values are not logged.
  - Fail-closed on a broken PostgreSQL table, while the rest of the gateway stays on PostgreSQL.
  - Schema, PK and CHECK/NOT NULL/JSONB constraints are enforced by the database. Nothing references the table.
  - DROP TABLE rollback, and an idempotent re-migration on restart.

## Data and deployment

- **Forward migration:** on boot, `CREATE TABLE IF NOT EXISTS app_settings` runs in PostgreSQL (inside `migratePostgresTables`, before the startup sync fires `onSync`) and in SQLite (`createTables`). JSON gets a new optional top-level member. No backfill. Existing tables are untouched.
- **Rollback or compensation:** `DROP TABLE app_settings` in PostgreSQL and/or SQLite, and optionally delete the `app_settings` member of the JSON file. Nothing references the table. The previous image never reads it, so rolling back the image without dropping the table is also safe. Dropping the table loses only the saved settings, and the server falls back to `.env` and the defaults.
- **Backward compatibility:** additive. An older image ignores the table. A newer image on an older database creates the table.
- **Data retention/deletion impact:** one row per key, overwritten in place, so the size is bounded (at most 64 KB per key). No history is kept and no purge is needed. Deleting a document is not in the contract (a "clear" is a save of the default document). There is no orphan risk because there are no references in either direction.
- **Deployment/restart required:** yes, a rebuild and restart to take effect. That is Hermes's integration step and is not performed here.

## Risks and follow-up

- **Known risks:**
  - Read-modify-write races in routes: `getAppSetting` followed by `saveAppSetting` can lose an update when two admin requests interleave (for example, two POSTs adding channels). Use `db.updateAppSetting` for channel add/patch/delete, route changes and per-gate overrides. Throw the route's own error inside `mutate` (for example `CHANNEL_IN_USE` / `CHANNEL_UNKNOWN`), and it rejects with nothing written.
  - JSONB normalises key order. Documents read back after a restart may list keys in a different order than they were written. Deep equality is unaffected.
  - The queue is per process. A second gateway process writing the same database would still be last-writer-wins. Only one gateway runs today.
- **Unresolved questions:**
  - Should `init-db.sql` also gain the `app_settings` DDL? It was not in my assigned files, and `login_events` / `stranger_faces` are not in it either. The runtime migration is authoritative.
  - Should values written during a fallback period ever be offered for re-import? They are only reported by key today.
- **Dependencies on other agents/commits:** none. This branch is based on `b22adf6`.
