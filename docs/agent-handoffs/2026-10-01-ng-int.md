# Agent handoff: ng-int (N gates, backend integration)

## Task

- **Title:** N-gate wave, backend integration: `server.ts`, `src/server/auth.ts`, `src/server/recording.ts` (plan `docs/plans/2026-09-29-scale-and-accuracy.md` Part E and section 11).
- **Owner/agent:** backend integrator (ng-int), delegated by Hermes/INT. Hermes merges and verifies.
- **Acceptance criteria:**
  - Gates are a list keyed by gate id. `entry`/`exit` are permanent (they can be disabled, not deleted). The legacy `entryGate`/`exitGate` stay as views and stay in storage.
  - Every route that takes a gate looks it up among the configured gates. An unknown, malformed or missing gate gets 400; there is no fallback to `entry`.
  - Admin routes `POST /api/gates` and `PUT`/`DELETE /api/gates/:gateId`.
  - Per-gate watchers, pipelines, stats and cooldowns. Events and stranger faces carry `gateId`.
  - Doors: a door list, lock state, timers and controller per door. A grant opens the gate's door. Tokens are never returned.
  - Logs: `gateId` filter and field, plus a CSV gate column. Recording channel per gate. Auth rules use the gate-id slug.
  - Typecheck, unit, build and integration gates pass on SQLite and PostgreSQL.
- **Scope explicitly excluded:** `db.ts`, `src/server/pipeline/**`, `src/types.ts`, `src/server/gates.ts`, frontend components.

## Changes

- **Behavior changed:**
  - **Camera config:**
    - The in-memory config has `gates: GateRecord[]`, with `entryGate`/`exitGate` as references to gates `entry`/`exit`. It is read with `gatesFromStoredConfig`, which accepts both shapes.
    - A missing `entry`/`exit` is re-created from the legacy key or from the defaults.
    - Both `gates` and the legacy keys are persisted.
    - Stream ids are prefixed with the gate id, so legacy ids such as `exit-501` do not change.
    - On load, a stored legacy key that differs from its gate entry was written by an older release after a rollback. That edit is adopted for the gate. This release always writes the two identically, compared with sorted keys because jsonb reorders them.
  - **Gate routes:**
    - Streams (`GET`/`POST`/`PUT`/`DELETE`), watch, pipeline-mode, snapshot (`?gate=`), scan-rtsp, template capture and `POST /api/recognize-face {gateId?}` all resolve a configured gate.
    - Unknown, malformed or **missing** gate: 400. This includes scan-rtsp and snapshot without `gate`, which used to default to `entry`.
    - Gate lookup lower-cases the parameter, so an old client sending `EXIT` still works.
  - **Scan type:** the gate's direction is the event type. A `scanType` in the scan-rtsp body is ignored; the dashboards send the gate's own direction anyway. `/api/recognize-face` without `gateId` keeps today's `scanType` mapping to `entry`/`exit`.
  - **`POST /api/camera-streams/config`:**
    - Takes `gates` (wins) or the legacy keys.
    - An old dashboard that echoes the whole served config (now including `gates`) with its edit in `entryGate` still works. A legacy field is taken when the echoed `gates` entry still holds what was served, and `gates` wins a real conflict. The existing streams test for this case passes.
    - The route never creates or removes a gate (unknown id: 400). It never changes `id`, `direction`, `doorId` or `pipelineMode` (current values are kept).
    - **Security fix:** before this change an operator could set `pipelineMode` through this route, which bypassed the admin-only `/pipeline-mode` route.
  - **Gate admin routes:**
    - `GET /api/gates` (viewer): a summary with no URLs.
    - Success answers of `POST`/`PUT`/`DELETE /api/gates` carry the full camera config (`config`) and a `summary`. Refusals are `{success: false, error}`.
    - `POST /api/gates {id, label, direction, doorId?}`: 201. Returns 400 for a bad or reserved id (`config`, `watch`, `snapshot`, `scan-rtsp`, …), a bad direction, a missing label or an unknown door, and when `MAX_GATES` is reached. Returns 409 for a duplicate.
    - `PUT /api/gates/:id {label, direction, doorId, enabled}`: the direction of `entry`/`exit` is fixed (400).
    - `DELETE /api/gates/:id`: 400 for `entry`/`exit`. It stops the gate's watcher and pipeline and drops its stats and cooldown entries. Its history is kept.
    - A new gate starts enabled, with one empty RTSP stream `<id>-primary` and the watcher OFF.
    - Every config mutation has an actor-attributed console line (`[Gates]`, `[Camera Config]`, `[Door Config]`, `[Lock]`, `[Gate Watch …]`, `[Pipeline …]`). CSRF is enforced by the global boundary.
  - **Per-gate state:** watchers, outcome stats, pipelines and pipeline error logs are Maps keyed by gate id. They are synced with the configured gates: start, stop and drop on add, remove, enable and direction change.
    - `GateWatchRuntime` gains `gateId` and `gateLabel`; `gate` stays the direction.
    - `pipelineModeFor(gateId)` uses the gate's `pipelineMode`, else `PIPELINE_MODE_<gateEnvSuffix(id)>`, else legacy.
    - The pipeline receives gate ids, per the ng-pipe INT to-do. That includes the silent `nearestLegacyEvent` bug, now `gateIdForLegacyRow(log) !== gate`.
    - Log tags keep `ENTRY`/`EXIT` for the two legacy gates and use the id for any other gate.
    - A scan whose gate was removed mid-flight records nothing and opens nothing (409 `GATE_REMOVED`).
  - **Events:**
    - Every access log written has `gateId`, as do stranger faces. Cooldown keys use the gate id.
    - GRANTED/DENIED logs, notifications and the stranger webhook use the gate's door name.
    - Webhook titles stay per direction. For gates other than `entry`/`exit` the grant text gets ` - <gate label>`. Messages for the two legacy gates are byte-identical to before.
  - **Doors:**
    - The door controller config is `{legacy fields = door "main", doors: DoorRecord[]}`, with `main` first and mirroring the top-level fields.
    - `POST` takes `doors` as the whole door set or, from older clients, top-level fields that patch `main`. Door ids are validated, duplicates rejected, and the list capped at `MAX_DOORS`. Removing a door that a gate uses: 409. A door being removed while open is closed first through its own controller.
    - An absent `apiToken` keeps the stored token, as today.
    - **No response carries a token.** GET, POST, the door test and the `door_config_updated` SSE are built by `publicDoorConfig`. It strips `apiToken` at the top level and per door and adds `hasApiToken: boolean`; the sanitiser lets boolean `has*` flags through.
      - Note for review: the ng-ui handoff says the GET returned the raw token. On this server it never did, because the global `sanitizePublicJson` turns `apiToken` into `apiTokenConfigured`. The UI read `hasApiToken`, though, so it is now sent explicitly.
    - Auth type `"NONE"` can be stored (the UI offers it), but dispatch refuses it, as it refuses any unknown scheme. Such a command would go out without the token, so it fails closed and logs why.
    - Enum fields (`authHeaderType`, methods) are now validated and fall back to the current value. Before, any string was stored.
    - The destination guard covers every new door URL (refused: 400, nothing saved).
    - Lock state, countdown and relock timer, and controller dispatch are per door. `unlockDoor`/`lockDoor`/`sendDoorControllerCommand` take a `doorId` (default `main`). A grant opens `doorIdOf(gate)`.
    - Lock state goes through `db.getDoorLockState`/`saveDoorLockState`/`deleteDoorLockState`. For door `main` the store also writes the legacy `smart_lock_state` row, so `saveSmartLockState` is no longer called. Non-main doors are refreshed on PostgreSQL sync.
    - The startup destination audit covers every door URL.
  - **Lock routes:**
    - `GET /api/lock/status` and the new alias `GET /api/lock/state` take `?doorId=` (default `main`). An unknown or malformed door: 400.
    - New `GET /api/lock/states` returns every configured door.
    - `POST /api/lock/unlock|lock {doorId?}`, and the door test route takes `doorId`.
    - Responses carry `doorId`.
  - **Logs:**
    - `GET /api/logs` (and `/stats`, `/export.csv`) accept `gateId`. Malformed: 400. A well-formed unknown id is accepted, so a deleted gate's history stays filterable.
    - Public logs and SSE logs carry `gateId` (derived for old rows); `sanitizePublicJson` whitelists it.
    - The CSV gains a `Cổng` column after `Loại`, holding the label from the current config, else the id.
  - **Recording:**
    - `recording.ts` keys channels by gate id, from `RECORDING_<gateEnvSuffix(id)>_CHANNEL`. The legacy names are unchanged.
    - `/api/logs/:id/recording` uses the event's stored `recordingChannel` first (digits only), else the event's gate channel.
    - `/api/recordings/config` `gates` has a flag per configured gate id plus the legacy `ENTRY`/`EXIT` keys. Gate ids are lower-case, so the two never collide.
  - **Template coverage:** `configuredCameras` lists every gate's streams, with `gateId` and `gateLabel` (`gate` stays the direction).
  - **Boot log** lists every gate with its direction, door and stream count.
  - **`auth.ts`:** `(entry|exit)` becomes the slug `[a-z][a-z0-9-]{1,31}` with the same roles. A non-slug segment keeps the admin default. `/api/gates` writes are admin and reads are viewer.
- **API/event contracts added or changed:** everything above.
  - SSE for the frontend: door `main` keeps `lock_state` / `lock_countdown`, now with `doorId: "main"`. Every other door uses **`door_lock_state` / `door_lock_countdown`** (payload with `doorId`). An older dashboard (`App.tsx` treats any `lock_state` as the main lock) therefore never shows another door as the main lock.
  - `gate_watch_result` gains `gateId`. The `outcome` summary gains `doorId`.
- **Schema/migration changed:** none here (ng-db owns it).
- **Environment/configuration changed:**
  - `PIPELINE_MODE_<ID>` and `RECORDING_<ID>_CHANNEL` for gates beyond entry/exit, e.g. `PIPELINE_MODE_SIDE_DOOR` and `RECORDING_SIDE_DOOR_CHANNEL`. The legacy names are unchanged.
  - `measure-stream.ts --gate` takes a gate id (`entry`, not `ENTRY`).
- **Security/privacy impact:**
  - Fail-closed lookups everywhere: no default gate and no default door for an unknown id.
  - The door binding and direction are admin-only. An operator can no longer set `pipelineMode` through the config POST.
  - Door config responses are built without any token (`publicDoorConfig`: `hasApiToken` at the top level and per door). `sanitizePublicJson` stays as a second layer. Integration tests assert that neither the token nor an `apiToken` key appears in the GET, POST, door-test or lock-state responses. The gateway logs of both final runs were grepped for the test token: 0 hits.
  - Auth `NONE` never dispatches (fail closed, tested).
  - Removed doors are closed before removal.

## Data and deployment

- **Forward migration:** none in this branch. ng-db's additive columns and tables apply at boot. The camera config gains `gates` on the first save. Until then it is derived from the legacy keys on every load.
- **Rollback or compensation:**
  - The previous image reads the legacy `entryGate`/`exitGate`, which are always persisted, and ignores `gates`, `gateId` and `door_lock_states`.
  - Under the previous image, extra gates are inert: no watcher, and their events read as entry/exit by type.
  - If the old image edits a legacy key, that edit is adopted on roll-forward (see above).
- **Backward compatibility:**
  - The legacy config POST still works, as do legacy webhook texts for entry/exit, legacy env names, `GET /api/lock/status`, `lock_state` SSE for main, `gate` = direction in watch runtimes and in the watch/pipeline-mode responses, and `ENTRY`/`EXIT` recording flags.
  - Intentional changes: a missing or unknown gate is now 400 everywhere; `scanType` in the scan-rtsp body is ignored; the config POST cannot change `pipelineMode`/`doorId`/`direction`.
- **Data retention/deletion impact:** none new. Deleting a gate keeps its events and faces (they keep their `gateId`). Deleting a door deletes only its non-biometric `door_lock_states` row.
- **Deployment/restart required:** yes (rebuild), but only after integration review and the ng-ui merge, and with explicit owner approval. Do not deploy this branch alone.

## Risks and follow-up

- **Known risks:**
  1. **The door list (`doors`) is not persisted. Decide before any site uses a second door.** The SQLite `door_controller_config` table has fixed columns, and `db.getDoorControllerConfig`/`saveDoorControllerConfig` (unchanged by ng-db) drop `doors`. PostgreSQL never stored this config.
     - The server keeps the in-memory list across re-reads, so it works until a restart. After a restart, extra doors are gone.
     - A gate bound to a vanished door then fails closed: a grant is recorded and the door's state changes, but no controller command is sent.
     - Single-door installations are unaffected.
     - Proposed fix (data-migrations, `db.ts` + `init-db.sql`): a `doors` TEXT/JSONB column (`doors_json`) round-tripped by get/save, mirrored to PostgreSQL like the camera config. No server change is needed: `normalizeDoorControllerConfig` already prefers stored `doors`.
  2. Frontend token indicator: resolved. The server now sends `hasApiToken`, which ng-ui reads.
  3. **Frontend lock SSE (follow-up, as agreed):**
     - Non-main doors use `door_lock_state` / `door_lock_countdown`; door "main" keeps `lock_state` / `lock_countdown`, so `App.tsx` stays correct as it is.
     - A per-door lock view can listen to those events, or poll `GET /api/lock/states`.
  4. Pre-existing, not new: the door page echoes `apiUrl` as served. `redactedUrl` masks credentials or a token embedded in the URL, so saving such a URL unchanged would store the masked form. Only URLs with embedded credentials are affected. Recommend token-in-header auth types.
  5. Gate ids can be re-created after deletion. The new gate then shares the old history under the same id. The contract says ids are never reused, but this is not enforced, because enforcing it needs a tombstone list.
  6. `unlockDoor` does not await `db.saveDoorLockState` (ng-db suggested awaiting where a response depends on durability). The in-memory state is authoritative for the moment, the controller call should not wait on a DB write, and the store never rejects. Failures are logged at most once a minute.
  7. `GET /api/logs/stats` passes ng-db's `byGate` through as is. Configured gates with zero events are not merged in (ng-db's open question 2); the UI can merge them from `/api/gates`.
  8. The legacy-edit adoption on load is a heuristic: any difference between a stored legacy key and its gate entry. This release never writes them differently.
- **Unresolved questions:**
  1. Should the webhook grant text for `entry`/`exit` also carry the gate label? I kept those messages byte-identical.
  2. Should `POST /api/gates` accept initial `streams`? Today streams are added through the operator streams routes, which are destination-guarded.
