## Changes

- **Files changed:** `src/server/db.ts`, `init-db.sql`, three new test files above, this handoff.
- **Behavior changed:**
  - `stranger_faces` store. Exactly ONE store holds faces at a time: PostgreSQL when it is the active authority,
    else native SQLite, else JSON. No local mirror while PostgreSQL is active (biometric bytes must not escape
    retention). While PostgreSQL is configured but still connecting, or if its `stranger_faces` DDL failed,
    `saveStrangerFaces` returns `false` and reads are empty (explicit refusal, never parked locally).
  - `saveStrangerFaces` is all-or-nothing and awaited: a malformed face, or a face whose access event is not
    stored, refuses the whole batch (`false`, nothing written). PostgreSQL: one multi-row
    `INSERT ... ON CONFLICT DO NOTHING` after settling in-flight `saveAccessLog` writes for those logIds (bounded
    2 s, existing mechanism), FK enforces the event. SQLite: `BEGIN IMMEDIATE`, event existence check,
    `INSERT ... ON CONFLICT DO NOTHING`, `COMMIT`. JSON: staged array written atomically (temp + rename) before the
    in-memory swap.
  - Idempotency: replay by id is a no-op; additionally a unique `(logId, faceIndex)` index makes a writer's retry
    of the same frame with fresh ids a no-op (first row per slot wins, returns `true`).
  - Validation (`normalizeStrangerFace`, exported): required and refused if malformed - id (`SF-...`,
    `^[A-Za-z0-9][A-Za-z0-9._:-]{0,63}$`), logId (<= 64 printable ASCII), faceIndex (int 0..1000), capturedAt (ISO,
    normalised to UTC ms like access-log trace), gate, engine, box (4 finite), detectorScore/quality (|v| <= 1e6),
    sizePx (0..100000, rounded), embedding (<= 4096 values, |v| <= 1e6), modelTag (<= 128), crop (Buffer <= 2 MB).
    Dropped to NULL if malformed (never truncated, never fatal): streamId, trackId, sourceWidth/Height, edgeEnergy.
    Input `purgedAt` is ignored.
  - Pages: `(capturedAt DESC, id DESC)` keyset, strict `<` cursor, limit clamped 1..100, purged rows excluded, no
    crop. PostgreSQL `id` and `capturedAt` are `COLLATE "C"` so ordering is bytewise exactly as SQLite/JSON.
  - `getStrangerFacesByIds`: unknown/non-string ids skipped, purged included, no crop.
  - `getStrangerFaceCrop`: `undefined` for unknown, purged, or a face stored without crop.
  - `purgeStrangerFaces(cutoffIso, keepIds)`: single UPDATE (PG/SQLite) clearing crop + embedding and setting
    `purgedAt`; dims/modelTag/box/scores/logId kept as the tombstone. Idempotent. Unparseable cutoff throws
    `RangeError` (a retention job must not silently purge nothing). With PostgreSQL active it also purges faces
    stranded in the local SQLite/JSON store by an earlier fallback period (logged, not counted); stranded unpurged
    local faces are reported at startup.
  - Extra (not in the contract, additive): `getStrangerFacesByLogIds(logIds)` ordered by logId, faceIndex, purged
    included, no crop - for the `#strangers/<logId>` lookup and for re-reading ids after a retried write.
  - Resolutions: `faceIds` normalised sorted on commit/save/restore, written to both tables, read back as `[]` for
    old rows; `sameResolutionIntent` compares faceIds as sorted sets (missing = `[]`); restore checks faceIds.
    Every read returns `faceIds` (always an array).
  - `getRetiredStrangerObservationIds()` adds `face:<id>` per faceId.
  - `getStrangerCandidateLogsPage()` excludes logs with any face row (purged or not: a purged face still represents
    its event); PostgreSQL `AND NOT EXISTS (SELECT 1 FROM stranger_faces sf WHERE sf."logId" = access_logs.id)`,
    only once the table exists.
  - `clearAccessLogs()` (admin wipe) removes the faces of the cleared events (PG `ON DELETE CASCADE`, explicit on
    SQLite/JSON).
- **API/event contracts added or changed:** none at HTTP level. Store contract implemented as written; see
  "Contract notes" below for the stricter-than-written behaviours.
- **Schema/migration changed:** yes (additive), see Data and deployment.
- **Environment/configuration changed:** none.
- **Security/privacy impact:** crops never in pages; embeddings are returned by the store (server-side) and must be
  stripped by INT before any API response (`publicAccessLog`-style). Log lines never include crops or embeddings.
  No second copy of faces while PostgreSQL is active. Tombstones keep no biometric bytes (asserted on all stores).

## Data and deployment

- **Forward migration:** automatic at startup, additive, no backfill (owner decision 3).
  - PostgreSQL: `ALTER TABLE stranger_resolutions|stranger_resolution_events ADD COLUMN IF NOT EXISTS "faceIds"
    JSONB NOT NULL DEFAULT '[]'::jsonb` (constant default: catalog-only, no rewrite) in the main schema batch;
    `stranger_faces` + indexes in a SEPARATE statement so a failure there cannot roll back the existing migration
    (logged; faces then refused, candidate page unchanged). `init-db.sql` carries the same DDL for new databases.
  - SQLite: `ALTER TABLE ... ADD COLUMN faceIds TEXT NOT NULL DEFAULT '[]'` (duplicate-column error = already done),
    `CREATE TABLE/INDEX IF NOT EXISTS stranger_faces`.
  - JSON: new optional key `stranger_faces`; resolutions without `faceIds` read `[]`.
- **Rollback or compensation:**
  - To the previous image: no DDL needed (tested on PG and SQLite). Old code never names `faceIds` (its INSERTs get
    the default, its explicit SELECTs ignore it) and never reads `stranger_faces`. Per the plan, captures resolved
    per face (empty logIds) reappear as open log-level groups; nothing is lost. Old `clearAccessLogs` still cascades
    to faces on PG.
  - Full schema removal (optional, irreversible for face membership - `pg_dump -t stranger_faces -t
    stranger_resolutions -t stranger_resolution_events` first): `DROP TABLE stranger_faces; ALTER TABLE
    stranger_resolutions DROP COLUMN "faceIds"; ALTER TABLE stranger_resolution_events DROP COLUMN "faceIds";`
    Tested: adjudications survive, a restart re-applies the migration idempotently.
- **Backward compatibility:** `StrangerResolutionRecord.faceIds` is optional on input and always present on output;
  existing log-only callers behave as before (`[]` on both sides of every comparison).
- **Data retention/deletion impact:** crops/embeddings are cleared by `purgeStrangerFaces` (INT schedules it; owner:
  14 days, `FACE_STRANGER_FACE_RETENTION_DAYS`). Tombstones (box, scores, dims, modelTag, logId, times; no biometric
  bytes) are kept indefinitely for audit and to keep their event out of the log-level candidates - no deletion
  policy for tombstones yet. Faces are deleted with their access event (admin clear). Stranded local faces are
  purged on the same clock. Legal hold: out of scope (plan section 6). Orphans cannot occur: FK on PG, same-
  transaction event check on SQLite/JSON, cascade on clear.
- **Deployment/restart required:** yes, as part of the integrated per-face release (migration runs at startup).
  Not deployed.

## Risks and follow-up

- **Known risks:**
  - `(logId, faceIndex)` dedupe: the writer MUST give each face of one access event a distinct `faceIndex`. If the
    pipeline links several person-tracks to the same DENIED event with the same index, later ones are silently
    treated as retries (`true`, not stored).
  - Faces written while running on the local fallback are not visible once PostgreSQL is back (same class as
    access logs written during a fallback); they are reported at startup and purged on the retention clock, not
    copied.
  - JSON fallback candidate paging keeps its existing insertion-order semantics (not timestamp order), now also
    skipping logs that have faces.
- **Unresolved questions:** tombstone lifetime (keep forever vs. delete with the access-log retention decision still
  open in plan section 7.1).
- **Dependencies on other agents/commits:** none; INT consumes the methods below.
- **Contract notes (no change to `src/server/strangerFaces.ts` needed):** stricter than written - dedupe also by
  `(logId, faceIndex)`; `false` for an unknown access event, a malformed face, or PostgreSQL not ready; purge throws
  on an unparseable cutoff; additive `getStrangerFacesByLogIds`.
- **Requested integration action/order (INT, server.ts - proposals only):**
  1. Writer (`applyRecognitionOutcome`, pipeline stranger outcome): `await db.saveAccessLog(log)` first (or at
     least issue it first; db settles it up to 2 s), then `await db.saveStrangerFaces(faces)` with faceIndex
     0..n-1 per event; on `false` log and continue - the access event is already stored and the door outcome is
     untouched.
  2. Resolve/dismiss/merge/quick-register/restore: put `faceIds` (from `parseObservationIds`) on every
     `StrangerResolutionRecord`; `sameResolutionIntent` pre-checks then treat other face members as a conflict.
     The restore route (server.ts ~7690) compares only `logIds` itself before calling
     `db.restoreStrangerResolution`; compare `faceIds` too for a clean 409 (db already throws `restore-conflict`,
     mapped to 409 at ~7713).
  3. Lookup (`/api/strangers/lookup`, ~7338): `getStrangerCandidateLogById` is unchanged and still returns a log
     that has faces; call `db.getStrangerFacesByLogIds([logId])` first and open the group of the first face; the
     retired check should also consider `face:<id>` of those faces.
  4. Retention job: daily `db.purgeStrangerFaces(new Date(Date.now() - days * 86_400_000).toISOString(), keepIds)`
     with `days = strangerFaceRetentionDays()` (0 = disabled) and `keepIds` = `faceIds` of current
     `QUICK_REGISTER`/`MERGE` resolutions (`db.getStrangerResolutions()`).
  5. `GET /api/strangers/faces/:id/image`: `db.getStrangerFaceCrop(id)` -> 404 when `undefined`.
  6. Strip `embedding` from face records in every API response.
