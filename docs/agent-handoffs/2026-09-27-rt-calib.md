# Agent handoff: CALIB - cheapest good-enough recogniser for the pipeline flow, compute sizing

## Task

- **Title:** Calibrate the cheapest face recogniser that is good enough on this site's own captures, for the
  NEW real-time pipeline flow only; size the compute the owner should buy; wire a pipeline-only recogniser
  selection with its own template tag; design how the pipeline's gallery is derived for a second tag.
- **Owner/agent:** CALIB (face-engine), 2026-09-27.
- **Acceptance criteria:**
  - Candidates measured on this site's captures: TAR at FAR = 0 and 1e-3, cosine distributions (genuine /
    impostor p5/p50/p95), per-model thresholds reproducing the r50 operating point, embedding latency at 1 and
    2 ORT threads, ratio vs r50. "Good enough" = TAR@FAR=0 within 2 points of r50 AND impostor p95 at least
    0.08 below the calibrated accept threshold.
  - Fewer embeddings per person measured (k = 1, 2, 3, 5 best frames).
  - Compute sizing (vCPU, GPU option) from the winner's latency; CUDA EP feasibility checked without
    installing anything.
  - `PIPELINE_RECOGNIZER_MODEL` / `PIPELINE_RECOGNIZER_VARIANT` for the gate workers, tag derived from the
    file; default behaviour unchanged (tested); legacy engine untouched (tested); gallery-derivation design +
    pure function with tests.
  - Gates: typecheck, unit, build.
- **Scope explicitly excluded:** `server.ts`, `db.ts`, `types.ts`, `contracts.ts`, compose, Dockerfile,
  `.env.example`; implementing the gallery derivation beyond the planner; any change to the legacy
  recogniser, its thresholds or its templates; deployment.

- Weak labels: the employee id of a GRANTED row is the legacy r50 decision itself. Two label defects were found
  from the embeddings alone (no image was viewed):
  1. **EMP-0465 is almost certainly the same person as EMP-7602**: its single crop matches 81 of EMP-7602's 88
     crops at cosine 0.40-0.66 (the whole strict-impostor tail of every model was this one pair). It is excluded
     from scoring (`--exclude EMP-0465`, declared in the report). The owner should check whether EMP-0465 and
     EMP-7602 are one person with two records, or a false accept at the entry door on 2026-09-20 10:42 UTC.

- The stored snapshots carry the annotator's green box (outside the aligned face; alignment is unaffected, the

### Recommendation

1. **Pipeline recogniser: `PIPELINE_RECOGNIZER_VARIANT=r50_int8`** (`w600k_r50_int8.onnx`, tag
   `arcface_w600k_r50_int8`), thresholds `acceptSingle 0.56, acceptFused 0.48, minEvidence 0.35, minAgreeing 2,
   minMargin 0.08` (`PIPELINE_FUSION_THRESHOLDS_BY_TAG`). It is the cheapest model that keeps r50's operating point:
   4.3x faster, drift under 0.02, TAR within 1.4 points at FAR 1e-3, 0 strict false accepts, impostor p95 0.13
   (margin 0.43 to the accept threshold, far above the 0.08 fusion margin). Caveat, stated: on the FAR = 0
   statistic it is 5 points under r50, but that statistic is set by the single highest of 5,503 impostor pairs
   (0.473 vs 0.455) and moves by 12 points between INT8 recipes that differ by 0.001 in drift; I do not consider it
   decisive with 3 effective identities. Re-check on the shadow comparison before `live`.
2. **mbf: shadow measurement only.** Selectable (`PIPELINE_RECOGNIZER_VARIANT=mbf`, own tag, calibrated
   `0.51 / 0.45 / 0.32`), 15x cheaper, but 7-8 TAR points under r50 on this site: not good enough as the sole
   decision model. It would need a GPU-less budget so tight that r50_int8 cannot fit (see sizing), and then only
   with a per-camera gallery and a larger gallery per person.
3. **Templates per person: 5 per camera** (cap 5 in the planner is per employee; if INT wants per camera, use
   cap 5 with `streamId` grouping as implemented and raise the cap to 8-10 for two cameras).
4. The two label findings (EMP-0465 = EMP-7602? and EMP-8922's second face at EXIT) go to the owner regardless.

## Compute sizing

### CUDA execution provider (checked, nothing installed)

- `onnxruntime-node` 1.30.0 ships `libonnxruntime_providers_cuda.so` (272 MB) for linux-x64 in the npm package. Its
  sonames are `libcudart.so.13`, `libcublas.so.13`, `libcublasLt.so.13`, `libnvrtc.so.13`, `libcurand.so.10` and
  `libcudnn.so` (9.x): it needs the **CUDA 13.0 runtime + cuDNN 9** (ORT's table: 1.27-1.30 default GPU builds
  are CUDA 13.0 / cuDNN 9; a CUDA 12.8 build exists only for the Python/NuGet packages, not for npm).
- Probe on this host: `InferenceSession.create(file, { executionProviders: ["cuda"] })` fails with
  `Failed to load library ... libcublasLt.so.13: cannot open shared object file` and falls back cleanly to CPU
  when `cpu` is listed second. No GPU is present (`lspci`: Cirrus VGA only).
- The runner image **deletes** the CUDA/TensorRT provider libraries (`Dockerfile`, node_modules trimming), so a GPU
  deployment needs: a passthrough GPU on the VM, the NVIDIA driver on the host, `nvidia-container-toolkit`
  (`--gpus all` in compose), the CUDA 13 runtime + cuDNN 9 libraries in the image (~2.5-3 GB more; e.g. base
  `nvidia/cuda:13.0-cudnn-runtime-ubuntu24.04` with Node added), the provider libraries kept, and
  `executionProviders: [{ name: "cuda" }, "cpu"]` in `faceEmbedding.ts` behind a `FACE_ORT_EP=cuda` switch
  (fail closed if requested and not loadable). None of that is done here.
- Expected GPU-side speed (published/architectural numbers, not measured here): ArcFace r50 at 112x112 is ~4
  GFLOPs, MobileFaceNet ~0.45 GFLOPs, SCRFD det_10g at 640 ~10 GFLOPs. On an entry-level datacenter GPU (T4,
  8 TFLOPS FP32) that is ~3-6 ms per r50 face, ~1-2 ms per mbf face and ~8-15 ms per 640 detector frame at batch
  1 including launch overhead (InsightFace's own benchmarks report det_10g at 640 in ~5 ms and r50 in ~2-3 ms on
  faster GPUs). Against the CPU medians below that is roughly 50-100x for r50 and 20-50x for the detector: with a
  GPU the recogniser choice stops mattering and the detector, not the recogniser, sets the frame rate; decode
  stays on the CPU (or NVDEC, which FFmpeg in the image does not include).

### vCPU sizing from the measured latencies

Method: a 1-thread median is used as the CPU-time of one call (core-seconds); per gate at 4 frames/s with up to 3
faces per frame, cores = 4 x (detector + faces x recogniser) + decode. Detector numbers are PERF's on the same
host and cap (SCRFD 640: INT8 256 ms, FP32 820 ms at 1 thread). Decode from the brief: entry 1.25 cores full
frame / 0.8 with the ROI, exit 0.5. Align/quality/tracker are a few ms per face and are inside the 30 % headroom.
All latencies were measured under host load 5-8, so they are ~20-30 % pessimistic; the sizing is conservative.

| configuration (both gates) | inference, worst case 3 faces every frame | inference, typical (tracker embeds ~1 face/frame while people are in view) | + decode (1.25 + 0.5) + legacy gateway/HTTP/DB (~1) | total x 1.3 headroom: worst / typical |
|---|---|---|---|---|
| INT8 detector + **r50 FP32** (today) | 2 x 4 x (0.256 + 3 x 0.679) = **18.4** | 2 x 4 x (0.256 + 0.679) = 7.5 | 2.75 | **27 / 13 cores** |
| INT8 detector + **r50_int8** (recommended) | 2 x 4 x (0.256 + 3 x 0.157) = **5.8** | 2 x 4 x 0.413 = 3.3 | 2.75 | **11 / 8 cores** |
| INT8 detector + mbf | 2 x 4 x (0.256 + 3 x 0.046) = 3.2 | 2 x 4 x 0.302 = 2.4 | 2.75 | 7.7 / 6.7 cores |
| FP32 detector + r50_int8 | 2 x 4 x (0.820 + 0.471) = 10.3 | 2 x 4 x 0.977 = 7.8 | 2.75 | 17 / 14 cores |
| ROI decode on entry (0.8) with r50_int8 | 5.8 | 3.3 | 2.3 | 10.5 / 7.3 cores |

Reading: with r50_int8 and the INT8 detector, the detector is the larger cost (1 core per gate at 4 fps); the
recogniser adds 0.6-1.9 cores per gate. Today the 8-core VM carries the soak gateway AND other stacks at a
baseline load of 5-7, so the gateway effectively has 1-3 cores: that, not the model, is why PIPE measured
0.6-1.0 frame/s.

**vCPU recommendation:** give the gateway **12 dedicated vCPUs** (worst case with headroom for r50_int8 + INT8
detector at 4 fps on both gates); **8 dedicated vCPUs is the floor** (typical load, no headroom for a third face
or a legacy scan burst). If the VM stays shared with the other stacks, add their baseline (5-7 cores) on top:
**16-20 vCPUs total**. Keep FP32 r50 only with a GPU (27 cores worst case on CPU is not sensible).

**GPU option:** any current NVIDIA datacenter/workstation GPU with >= 4 GB (T4/L4/A2 class, or a passthrough
consumer card) runs SCRFD 640 + 3 x r50 FP32 in ~15-30 ms per frame (published numbers), so both gates at 4 fps
use well under 10 % of it; the CPU need then falls to decode + JS, ~4-5 vCPUs, and the FP32 r50 and its existing
templates can stay (no re-enrolment under a new tag). Cost: CUDA 13 + cuDNN 9 in the image (~2.5-3 GB), the
provider libraries kept, nvidia-container-toolkit on the host, `FACE_ORT_EP=cuda` wiring with fail-closed
fallback (~1-2 days of INT work), and GPU passthrough on the VM. Not measured here (no GPU present).

**Cheapest path that meets the bar without new hardware work:** +4-8 vCPUs and `r50_int8` for the pipeline.

## Gallery derivation for the pipeline's tag (design; planner implemented, wiring proposed)

Today `face_templates` rows are `arcface_w600k_r50` (19 rows, 6 employees, sources `enrollment` 4 / `merge` 15),
each with `sourceLogId` and `streamId` when it came from a capture. A cheaper recogniser needs its own rows:

1. **Storage.** Same table, new rows with `modelTag = <pipeline tag>` (e.g. `arcface_w600k_mbf`), `source =
   "auto"`, `sourceLogId` = the picture's access-log id (or the r50 template's id for a template-source photo),
   `streamId` copied from the source, `quality` = the new embedding's capture quality. `buildGallery(templates,
   tag)` already separates tags, so the legacy gallery is unaffected by the extra rows. Cap: 5 per employee per
   tag (the tracker's evidence budget; the planner's default), so the gallery for 12 employees is <= 60 rows.
2. **Sources, in priority order** (`planGalleryDerivation`): the employee's enrolment photos (`employees.photo`
   / the enrolment upload, if still stored), then the snapshot behind each r50 template (`face_templates.sourceLogId`
   -> `access_logs.photoSnapshot`), then recent GRANTED access-log crops of that employee. Each source is
   re-detected and re-aligned by the pipeline's own detector path (`extractFaces` on the stored picture; for
   full-frame snapshots the pipeline's `faceCrop` geometry first) and embedded by the pipeline recogniser. A
   source that yields no clear face >= 60 px, or quality < 0.25, is skipped (the planner filters on the known
   quality; the executor re-checks after detection).
3. **Camera diversity.** Cross-camera cosine on this site overlaps the impostor range (memory note and the
   measured cross-gate row below), so the planner round-robins over `streamId`: each camera gets templates of
   its own before any camera gets a second one.
4. **Determinism and audit.** The plan is a pure function of (existing templates, candidate pictures, options)
   with a fixed ordering (kind, quality, capturedAt, id), so a re-run after a crash produces the same plan and
   skips what already exists (`alreadyDerived` by `sourceLogId`/template id). Every created row is an ordinary
   template row with provenance; nothing rewrites r50 rows or access events.
5. **Execution (server.ts / db.ts, INT-owned, not implemented here).** A job `deriveGalleryForTag(tag)` runs at
   pipeline start when `resolvePipelineRecognizer().modelTag !== faceModelTag()` and whenever templates/employees
   change: build the plan, embed in the face worker pool (bounded concurrency, off the main thread), insert rows
   via the existing `addFaceTemplate` path, log counts (never embeddings). Until an employee has >= 1 row under
   the tag, the pipeline simply cannot recognise them (fail closed as "stranger"); `plan.uncovered` names them.
   Enrolment and quick-register of a NEW employee should embed under BOTH tags at once (two rows, two tags) so
   the derived gallery does not lag.
6. **What the operator sees.** `/api/face-engine/status` `info` gains `pipelineRecognizer: {file, modelTag,
   variant, source, warning}` and `pipelineGallery: {modelTag, employeesCovered, employeesTotal, templates,
   uncovered: [employeeId...]}`; the pipeline stats line gains the tag. In the dashboard's pipeline card: the
   model name, "N of M employees enrolled for the pipeline model", and a per-employee badge "chua co mau cho
   pipeline" (no template for the pipeline model) with a "Tao mau" action that runs the derivation for that
   employee. Nothing shows embeddings or thresholds beyond what `/api/config/ai` already exposes.
7. **Retention/deletion.** Derived rows follow the employee: deleting an employee or a template source deletes
   its rows under every tag; the existing template deletion endpoints must filter by tag or delete all tags of
   the employee explicitly. Rows carry no image.

## Risks and follow-up

- **Known risks:**
  - Few identities (3 carry 94 % of the labelled crops) and weak labels: the tables are a site calibration, not a
    benchmark. The FAR = 0 statistic in particular is set by single pairs; the FAR = 1e-3, d' and operating-point
    rows are the stable ones. Re-check the winner in the MT shadow comparison before any `live` use.
  - INT8 r50 needs its own templates (tag `arcface_w600k_r50_int8`); until the derivation job exists, a worker on
    that variant fails closed (no context) - correct, but it recognises nobody. The stored-crop path measured here
    says the derived gallery will be at least as good as the frame path.
  - Legacy security findings (not model related): EMP-0465 vs EMP-7602 (probable duplicate or false accept) and
    EMP-8922's second face at EXIT (probable repeated false accept or a wrong `merge` template). Both need the
    owner; the second may warrant reviewing the 15 `merge` templates and the exit GRANTED events of EMP-8922.
  - Latencies measured under contention; the sizing is conservative by ~20-30 %.
  - `w600k_mbf.onnx` and `w600k_r50_int8.onnx` live in `/data/models/candidates` (not in the image) with
    `SOURCES.sha256`; the compose mount of `/data/models` (PERF proposal 4 / PIPE P2) is still pending.
- **Unresolved questions:**
  - Owner: buy +4-8 vCPUs (r50_int8) or a GPU (keep FP32 r50, no re-enrolment)?
  - INT: implement the derivation job per the design, per employee cap 5 (per camera?) - and which statuses the
    UI shows.
  - Should `mbf` stay selectable at all? It is opt-in under its own tag and harmless, kept for shadow measurement.
- **Dependencies on other agents/commits:** none for merging. PIPE's `pipelineWorkerEnv` (in `main`) is the
  only shared function touched. INT owns the `server.ts`/compose follow-ups above.
- **Requested integration action/order:**
  1. Merge `feat/rt-calib` (3 code/script commits + handoff) after `release/rt-pipeline` = `main` @ 89c7df0; no
     conflicts expected (additive hunks in `faceEmbedding.ts`, `faceFusion.ts`, `gatePipeline.ts`).
