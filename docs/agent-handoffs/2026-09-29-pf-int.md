## Changes

- **Behaviour:**
  - **Writer:** each unrecognised face in the stored frame that matches no employee on its own gets the stranger floors and the per-person cooldown separately. Every face that passes is written as a stranger_faces row with its crop.
    - The row is written only after the access event is stored (foreign key).
    - DENIED frames keep one log embedding (the best face that passed).
    - Tailgaters are linked to the first GRANTED event and written after the unlock.
  - **Grouping:** runs over `face:` records plus older `log:` captures. Cluster ids of log-only groups are unchanged.
  - **Resolve routes:** accept clusterObservationIds and sourceObservationId; clusterLogIds still works.
  - **Lookup:** `lookup?logId=` goes through the frame's faces; `lookup?faceId=` is new.
- **API:**
  - GET /api/strangers/faces/:id/image (viewer; same cross-site guard as /api/logs/:id/image, via the shared guardBiometricImage).
  - The SSE payloads stranger_dismissed, stranger_registered, stranger_merged and stranger_restored carry clusterObservationIds.
- **Schema:** see pf-db. Additive: the stranger_faces table plus faceIds on the resolution tables.
- **Environment:** FACE_STRANGER_FACE_RETENTION_DAYS (default 14; 0 disables), passed through in compose.
- **Security/privacy:**
  - Crops and embeddings stay server-side; no response contains an embedding (checked in the demo).
  - Crops are erased after 14 days, except for faces that became an employee.
  - Collection now includes tailgaters (owner decision).

## Data and deployment

- **Forward migration:** automatic at startup, additive (pf-db).
- **Rollback or compensation:**
  - Redeploy the previous image. The old code ignores stranger_faces and faceIds.
  - Groups resolved per face reappear as open groups (their logIds are empty) and can be resolved again.
  - Employees and templates stay valid.
  - An optional DROP is described in the pf-db handoff.
- **Backward compatibility:** old clients sending clusterLogIds keep working for whole-frame captures.
- **Data retention/deletion impact:** new face crops of about 20 KB each, erased after 14 days.
- **Deployment/restart required:** yes (image rebuild). Only after owner confirmation.

## Risks and follow-up

- **Known risks:**
  - The lookup/window caches are cleared on write and restore. The retention purge clears them when it removes something.
  - faceIndex must be unique per event. The writer numbers accepted faces 0..n-1; a skipped crop leaves a gap, which is allowed.
- **Unresolved questions (owner):**
  - How long to keep purged tombstone rows (forever, or tied to the undecided access-log retention).
  - Whether to tune the floors for faces near 60 px.
- **Requested integration action/order:** owner confirmation, then merge release/per-face into main, deploy, and check the first real multi-face capture.
