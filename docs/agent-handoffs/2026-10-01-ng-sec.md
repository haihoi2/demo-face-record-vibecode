# Agent handoff: ng-sec (N gates, security black-box tests)

## Findings first

Every finding has a failing test in `tests/integration/nGatesSecurity.test.ts`. The test name starts with
`FINDING NGSEC-<n>`. Each test asserts the SECURE behaviour, so it fails until the defect is fixed. The tests
were not weakened. Every finding reproduced on both SQLite and PostgreSQL (fresh gateway, image
`smartface-tests:ngates` = `dba539aa3cd0`, built from `b9da1ff`).

Severity reflects physical-access and history-integrity impact under this deployment's roles (admin >
operator > viewer).

### NGSEC-1 (High): an operator's camera-config save silently reverts concurrent admin gate decisions

- **Route:** `POST /api/camera-streams/config` (operator). It races with `DELETE /api/gates/:id`, `PUT /api/gates/:id`,
  `POST /api/gates`, `POST /api/camera-streams/:gate/pipeline-mode` (admin), and with the stream and watch routes.
- **Root cause:** `server.ts`, `app.post(CAMERA_CONFIG_ROUTES)`:
  1. It reads `current = loadCameraStreamsConfig()`.
  2. It then runs `await cameraStreamsSaveCheck(...)`, the destination guard, which does a DNS lookup for every NEW
     stream host name.
  3. Finally it calls `commitCameraConfig(updated)`, with `updated` built from the stale `current`.

  Every gate change committed during the await is lost. The stream routes and the door-config POST already
  re-read after their await; this route does not.
- **Impact (each answered 200/201 to the admin):**
  - A deleted gate comes back: it is in the config, its watcher runtime runs again, and its tombstone is lost, so
    the id can be reused.
  - A gate the admin disabled is enabled again.
  - A door rebinding is undone, so grants at that gate open the OLD door.
  - A direction change is undone.
  - A newly created gate vanishes.

  An operator can trigger this on purpose and repeatedly, which overrides admin-only physical-access decisions.
- **Preconditions:**
  - An operator session.
  - A body with any new stream URL whose host is a NAME. The DNS round trip is the window: 60-130 ms here with a
    `.invalid` name. The save still succeeds, with a `DEST_UNRESOLVED` warning.
  - An admin change that lands inside the window.
- **Repro (black box):**
  1. As admin: `POST /api/gates {"id":"zv","label":"x","direction":"EXIT"}` returns 201.
  2. As operator, without awaiting the answer: `POST /api/camera-streams/config {"gates":[{"id":"<a scratch gate>","streams":[{"id":"<scratch>-primary"},{"id":"<scratch>-n","rtspUrl":"rtsp://itest-x.invalid:554/x","enabled":false}]}]}`.
  3. About 5 ms later, as admin: `DELETE /api/gates/zv` returns 200.
  4. Once both have answered, `GET /api/camera-streams/config` shows `zv` in `gates`, NOT in `retiredGateIds`, and
     `GET /api/camera-streams/watch` lists a runtime for `zv`.

  It reproduced 5/5 by hand and on every test attempt. Tests: `NGSEC-1a` (delete), `NGSEC-1b` (disable plus door
  rebinding).
- **Expected:** the config POST never overwrites changes it did not make. Either:
  - re-load the config after the await and apply the parsed patches to the fresh copy, as `POST /:gate/streams`
    does (`gatePatchesFrom` must be re-run against the fresh config, because a patched gate may have been deleted:
    answer 400 then); or
  - run the destination check on the candidate URLs BEFORE loading the config.
- **Regression test:** `NGSEC-1a`/`1b` (3 attempts each, slow-DNS window).
- **Owner:** INT (`server.ts`).

### NGSEC-2 (Medium): an operator can erase the retired gate ids, so deleted ids (and their history) get reused

- **Route:** `POST /api/camera-streams/config` (operator). Body: `{"retiredGateIds": []}`.
- **Root cause:** `const { entryGate, exitGate, gates, ...rootPatch } = body` and then `{ ...current, ...rootPatch }`.
  Every top-level key of the body reaches the stored config, including the server-owned `retiredGateIds` that
  `POST /api/gates` checks.
- **Impact:**
  - After the wipe, an admin (or the UI's label-derived id suggestion) can create a new gate with a deleted gate's
    id, in any direction and bound to any door.
  - `GET /api/logs?gateId=<id>`, `/stats` and the CSV then file the deleted gate's events under the new gate.
    History is re-attributed, which breaks the contract rule "ids are never reused" and the immutable-history
    invariant.
  - The same hole lets an operator ADD ids, which blocks admins from creating gates with those ids, and lets an
    operator inject arbitrary top-level keys into the stored config.
- **Repro:**
  1. Create and then delete gate `tomb`.
  2. As operator: `POST /api/camera-streams/config {"retiredGateIds":[]}` returns 200.
  3. As admin: `POST /api/gates {"id":"tomb","label":"x","direction":"EXIT"}` returns **201** (expected 409).
  4. Test `NGSEC-2` shows the tombstones going from N to 0.
- **Expected:** `retiredGateIds` is server-owned. The root patch is an explicit allowlist of the global fields an
  operator may change (for example `workerThreadsCount`). Unknown keys are ignored or answered with 400.
- **Owner:** INT.

### NGSEC-3 (Low): the retired-id list keeps only the last 256 ids

- **Root cause:** `DELETE /api/gates/:id` does `retiredGateIds: [...].slice(-256)`. After 256 further deletions, the
  oldest deleted id is accepted again, with the same history re-attribution as NGSEC-2. It takes about 8 s of
  scripted create/delete as admin.
- **Repro:**
  1. Create and delete `cap-first`.
  2. Create and delete 256 other gates.
  3. `POST /api/gates {"id":"cap-first",...}` returns **201** (expected 409). Test `NGSEC-3`.
- **Expected:** no cap. Alternatively, refuse any id that still has rows in `access_logs."gateId"` (db lookup), which
  also survives a config restore.
- **Owner:** INT (or data-migrations, for a db-backed check).

### NGSEC-4 (Low): a Unicode spelling resolves to an ASCII gate

- **Root cause:** `gateFromConfig` does `raw.trim().toLowerCase()` before the slug check, and `"K"` (KELVIN SIGN)
  lower-cases to `"k"`.
- **Effect:** `"Ksec-…"` names gate `ksec-…` in:
  - path parameters (`GET /api/camera-streams/<K>sec-…/streams` returns 200, `PUT /api/gates/<K>sec-…` returns 200);
  - the `scan-rtsp`/capture body `gate`;
  - the `recognize-face` `gateId`: the event is written under `ksec-…`.
- **Not a privilege bypass:** the auth table sees the percent-encoded segment as a non-slug, which keeps the admin
  default. The finding is that the contract's "unicode -> 400" does not hold.
- **Repro:** test `NGSEC-4`.
- **Expected:** validate the raw value against an ASCII pattern (`/^[A-Za-z][A-Za-z0-9-]{1,31}$/`) before
  lower-casing, or lower-case ASCII only.
- **Owner:** INT.

### NGSEC-5 (Low): non-string labels and ids are coerced, or crash with HTTP 500

- **Root cause:** `optionalTrimmedString` calls `String(value)`.
- **Effects:**
  - `POST /api/gates {"label":{"a":1}}` stores the label `"[object Object]"` (201).
  - `PUT /api/gates/:id {"label":["a","b"]}` stores `"a,b"`.
  - `{"toString":"x"}` makes `String()` throw `Cannot convert object to primitive value`, and the route answers
    **500** on:
    - `POST`/`PUT /api/gates` (admin);
    - the door list `label` (admin);
    - `POST /api/camera-streams/:gate/streams` `label` and `id` (**operator**).
  - No state was changed by the 500s seen here.
- **Repro:** test `NGSEC-5` (the failure lists every case and its status).
- **Expected:** 400 for any non-string label/id/text field at the route boundary.
- **Owner:** INT.

### NGSEC-6 (Medium; owner decision on "disabled"): a disabled gate still processes recognitions

- **Route:** `POST /api/recognize-face {"gateId":"<disabled gate>"}` (operator session or device token). By code
  reading, `POST /api/camera-streams/scan-rtsp` too, but that was not testable without a camera.
- **Root cause:** only the watcher checks `gate.enabled` (`server.ts` ~6045). The recognize and scan paths resolve
  the gate and proceed.
- **Impact:**
  - Disabling a gate (for example, a camera suspected of spoofing, or a door under maintenance) does not stop
    manual scans or device and API frames attributed to it.
  - The event is recorded at the disabled gate, and a GRANT there opens the gate's door.
- **Repro:**
  1. Create gate `dis` bound to a door.
  2. `PUT /api/gates/dis {"enabled":false}`.
  3. `POST /api/recognize-face {"imageBase64":<jpeg>,"gateId":"dis"}` returns 200 with a `log` at `dis`.
  4. Test `NGSEC-6`.
- **Expected:** 409 `GATE_DISABLED` with no event and no door command (recognize-face and scan-rtsp), or a written
  owner decision that "disabled" means "watcher off only".
- **Owner:** INT; decision: owner.

### NGSEC-7 (Medium): lock/unlock with a malformed `source` half-applies the door state and cancels the auto-relock

- **Route:** `POST /api/lock/unlock|lock {"doorId":..,"source":{"toString":"x"}}` (admin). `employeeName` and
  `/api/door-controller/test` with `updateDoorState` behave the same way.
- **Root cause:** `unlockDoor`/`lockDoor` work in this order:
  1. clear the door's timers;
  2. set `state`/`isLocked`;
  3. build ``Lệnh mở từ ${source}``, which throws;
  4. (never reached) broadcast, persist, controller command, relock timer.

  The route answers 500.
- **Impact:**
  - Unlock: the API reports the door UNLOCKED indefinitely. There is no relock timer, no SSE, no persistence and no
    OPEN command, so the API state and the physical state diverge.
  - Lock while the door is open: the pending auto-relock is cancelled and the API reports LOCKED, but no CLOSE
    command is sent. A physically open door is shown as locked and is never relocked by the timer.
- **Repro:**
  1. `POST /api/lock/unlock {"doorId":"<door>","source":{"toString":"x"}}` returns 500.
  2. `GET /api/lock/state?doorId=<door>` returns `UNLOCKED`, still `UNLOCKED` after `autoRelockSeconds` + 1.5 s.
  3. Test `NGSEC-7`. In a manual probe, `lock` with the same body answered 500 and reported LOCKED.
- **Expected:** validate `source`/`employeeName` as strings (bounded length) at the route and answer 400 before any
  state change. Also build all text before mutating state in `unlockDoor`/`lockDoor`.
- **Owner:** INT.

### Observations (no failing test; for the owner/INT)

- **O1 (design, Medium):** `POST /api/recognize-face {gateId}` lets every device-token holder and every operator
  pick the gate, and with it the DOOR a grant opens. Device tokens are not bound to a gate. A real ONNX match is
  still required for a grant. Before N gates, the choice was only entry/exit sharing door `main`. Proposal: bind
  device tokens to gate ids, or refuse `gateId` for gates whose door is not `main` unless the token is bound to
  that gate.
- **O2 (Low):** `POST /api/door-controller/test` with `testConfig` swaps the in-memory `doorControllerConfig` across
  an await and restores a stale snapshot afterwards. A door-config POST that lands meanwhile is lost in memory
  until the next reload, and lock routes read memory. The swap is dead code anyway, because
  `sendDoorControllerCommand` reloads the stored config. Proposal: delete the `testConfig` branch.
- **O3 (Low, audit):** the lock state's `lastActionBy` comes from the body's free-text `source`/`employeeName`, so an
  admin can write "<employee> (…)". The actor is only in the console line. Proposal: store the session actor.
- **O4 (Low):** gate and door labels keep control characters such as newlines. Labels appear verbatim in the
  `[Gates]`/`[Door Config]` console audit lines, so an admin can forge log lines. Not tested.
- **Consistent, not findings:**
  - Upper-case or space-padded gate ids in paths and bodies resolve to the same gate through lower-casing and
    trimming, as documented; `?gateId=` on logs is strict (400).
  - Routes are case-sensitive: `/API/...` is 401 for anonymous callers, 403 for a lower role, and 404 (writes) or the
    SPA shell (GET) for the admin. No data is returned.

### Limitation

There is no face fixture in the repo, and real biometric images are not used in tests. "A grant at the third gate
opens only its bound door" is therefore covered indirectly:

- a DENIED event at the third gate names the bound door (and the re-bound door after `PUT`);
- no door's state moves;
- the binding as `GET /api/gates` reports it;
- door-by-door lock isolation.

### What the suite covers (passing on both databases)

1. **Matrix: 26 routes x 4 roles.**
   - Anonymous callers get 401.
   - A lower role gets 403 `ROLE_REQUIRED`.
   - An allowed role reaches the route with a harmless body and never gets 401, 403 or 500.
   - Read access:
     - Viewer: `GET /api/gates`, streams, watch, lock state/status/states, logs, stats, CSV and recordings.
     - Operator: snapshot, streams writes, watch, scan-rtsp and template capture.
     - Admin: gates writes, pipeline-mode, door config GET/POST, door test, lock/unlock.
   - On every mutation, the allowed role is refused without CSRF, with a wrong CSRF token, with an evil Origin and
     with `text/plain` (415).
   - A final snapshot shows that no refused request changed a gate, door, stream, watch, pipeline mode or lock.
   - Case variants (`/API/Gates`, `/api/GATES/<id>`, `/API/Lock/Unlock`, `/API/Door-Controller/Config`, …) fail
     closed for every role.
2. **Validation:**
   - 36 malformed or reserved gate ids give 400, including traversal, case, unicode, fullwidth, 33 characters,
     empty, reserved words, SQL text, NUL and wrong JSON types. The 32-character boundary is accepted.
   - Malformed path gate ids give 400 or 404 on 8 routes, never 2xx or 500, and entry is untouched.
   - Bad query and body gates give 400 on snapshot, scan-rtsp, capture, recognize-face (no event written), logs,
     stats and CSV. A well-formed unknown id is an empty filter. `entry--` is a parameter, not SQL.
   - 13 bad door ids give 400 on the door list, unlock, lock, door test, gate binding, rebinding and lock
     state/status, plus query arrays and objects.
   - `MAX_DOORS`; `MAX_GATES` (also under a concurrent burst); duplicates 409; a deleted id is 409 in both
     directions and with whitespace.
   - Entry/exit cannot be deleted under any spelling or a concurrent burst. Their direction is fixed through
     `PUT`, the config `gates` patch and the legacy `exitGate` patch. An operator cannot change the third gate's
     direction or door.
3. **Secrets:**
   - Door tokens (a new door and `main`) appear as `hasApiToken` only, in GET/POST echo, door test, lock states,
     gates and door logs.
   - Omitting a token keeps it, `""` clears it, and echoing `hasApiToken`/`apiTokenConfigured` sets nothing.
   - A URL-embedded credential or token is redacted.
   - A camera password on the new gate's stream is redacted in config, streams, gates, watch, scan, the duplicate
     409 and the guard refusal.
   - A viewer SSE capture carries no secret. Other doors use `door_lock_state`, and `lock_state` only ever carries
     `main`.
   - Final scan: none of the 300+ responses seen by this file carries a secret. The gateway logs of both runs were
     grepped for the four test secrets: 0 hits.
4. **SSRF:**
   - The new gate's stream POST refuses loopback (4 spellings), metadata, link-local, unspecified, bad URL and the
     gateway itself (`DEST_SELF`), with status and code equal to exit's.
   - The stream PUT `rtspUrl` and HTTP_MJPEG `httpUrl`, the config `gates` patch, the scan-rtsp `url` and the
     snapshot `url` override are refused.
   - A private non-allowlisted host is handled the same as at exit. Strict allowlist run: `DEST_NOT_ALLOWED` for
     both.
   - The new door's `apiUrl` refuses loopback (4), metadata, link-local, unspecified and self, with the field
     `doors.<id>.apiUrl`, parity with `main`, and nothing saved. The private host is handled the same as for main.
5. **Isolation:**
   - Unlocking or locking door A leaves B and main untouched.
   - An event at the third gate names its door, follows a rebinding, and moves no door.
   - A deleted gate's events stay under its id in logs, stats, CSV and the unfiltered list. They never move to
     `entry`, and the id is never re-issued.
6. **Concurrency:**
   - 8 concurrent creates of one id give exactly one 201.
   - 5 concurrent deletes give exactly one 200.
   - Mixed creates, deletes and a PUT leave `config.gates` = `/api/gates` = the watch runtimes, with no duplicates
     or orphans and the tombstones kept.

## Risks and follow-up

- **Known risks:**
  - NGSEC-1 relies on a DNS round trip of at least 5 ms for an `.invalid` name. With a sub-5 ms resolver the test
    could miss the window and pass falsely; it never fails falsely.
  - NGSEC-3 adds about 10-20 s.
- **Unresolved questions:**
  1. Does "disabled gate" mean "watcher off" only, or "gate out of service"? (NGSEC-6.)
  2. Should device tokens be bound to gates? (O1.)
- **Dependencies on other agents/commits:** fixes belong to INT (`server.ts`): NGSEC-1, 2, 4, 5, 6, 7 and O2/O3.
  NGSEC-3 belongs to INT or data-migrations.
