## Changes

- **Files changed:** `src/server/db.ts`, `src/types.ts`, `init-db.sql`, `tests/accessLogTrace.test.ts` (new), `tests/integration/accessLogTracePersistence.test.ts` (new).
- **Behavior changed:**
  - `AccessLogRecord` / `AccessLog` gain `capturedAt?`, `trackId?` and `recordingChannel?`.
  - New export `normalizeAccessLogTrace()`. It validates before storage:
    - `capturedAt`: an ISO-8601 instant, years 2000-9999, stored normalised to `toISOString()` (UTC, ms).
    - `trackId`: `^[A-Za-z0-9][A-Za-z0-9._:-]{0,63}$`.
    - `recordingChannel`: `^[A-Za-z0-9_-]{1,16}$`; a non-negative integer is accepted and stringified.
    - An invalid value is stored as NULL and logged by field name only. The event itself is always stored. Values are never truncated.
  - New export type `AccessLogMeta`. `getAccessLogMetaById` returns id, timestamp, type, status and the three fields. On SQLite/JSON it now reads only those columns, not `SELECT *`.
  - `saveAccessLog(log)` now returns `Promise<boolean>` and never rejects:
    - `true` means the authoritative store (PostgreSQL when active, else SQLite/JSON) accepted the row or already had it.
    - `false` means that write failed.
    - Existing fire-and-forget callers compile and behave as before.
    - A replay with the same id is still a no-op; the first write, including its trace, wins.
  - Read-your-writes on PostgreSQL (commit `057b559`):
    - In-flight access-log inserts are tracked by id.
    - Single-event reads (`getAccessLogById`, `getAccessLogMetaById`, and so the stranger lookup and image routes) wait for that id's insert.
    - Pages, stats and stranger-candidate pages wait for all in-flight inserts.
    - Each wait is bounded at 2 s.
    - This fixes an existing race that was also present on the baseline: create a DENIED log and immediately look it up gave 404 `MISSING` for 2 of 40 pairs. After the fix: 0 of 40. It was also the cause of intermittent failures of `tests/integration/strangers.test.ts` on PostgreSQL.
- **API/event contracts added or changed:** `publicAccessLog` in server.ts spreads the record, so `/api/logs` responses and the `access_granted` SSE will carry the three fields once callers set them. They hold no secrets, paths or embedding bytes. Absent fields are omitted, not sent as `null`.
- **Schema/migration changed:** `access_logs` gains three columns:
  - `"capturedAt" VARCHAR(64)`
  - `"trackId" VARCHAR(64)`
  - `"recordingChannel" VARCHAR(16)`

  All are nullable with no default, and there is no index. SQLite uses `TEXT`. `init-db.sql` has them for fresh volumes.
- **Environment/configuration changed:** none at runtime. For tests only, the integration suite reads an optional `PERSISTENCE_PG_URL`: an admin URL of a throwaway PostgreSQL that is allowed to `CREATE DATABASE`. Without it, the 5 PostgreSQL persistence cases skip. The test refuses `smartface_db` and `smartface-postgres-18`.
- **Security/privacy impact:**
  - The fields are not biometric. They do link an event to NVR footage.
  - `recordingChannel` is charset-restricted so it can never inject into an NVR URL. The recording route should still validate it with the numeric `CHANNEL_RE` before use.
  - The values must be server-owned and never taken from request bodies (see the proposals).

## Data and deployment

- **Forward migration:** automatic at startup.
  - PostgreSQL: three `ALTER TABLE access_logs ADD COLUMN IF NOT EXISTS ...` in the existing startup DDL. A nullable column with no default is a catalog-only change: no table rewrite, just a brief ACCESS EXCLUSIVE lock that waits for running queries on `access_logs`.
  - SQLite: guarded `ALTER TABLE ... ADD COLUMN`.
  - JSON: fields simply appear on new rows.
  - No backfill: old rows keep NULL, and playback falls back to `timestamp`.
- **Rollback or compensation:**
  - Code rollback: redeploy the previous image. The columns stay and old code ignores them (verified with real code). Rows written during the rollback have NULL trace fields and read back undefined after rolling forward again.
  - Schema rollback, only if really required and only with the new code stopped (it would re-add the columns on its next start). This loses the trace values only, never events.
    - PostgreSQL: `ALTER TABLE access_logs DROP COLUMN IF EXISTS "capturedAt", DROP COLUMN IF EXISTS "trackId", DROP COLUMN IF EXISTS "recordingChannel";`
    - SQLite: `ALTER TABLE access_logs DROP COLUMN capturedAt;` and the same for the other two (supported by the SQLite bundled with Node 22).
    - JSON: nothing needed.
- **Backward compatibility:** all fields are optional, and every existing caller of `saveAccessLog` compiles unchanged. `getAccessLogMetaById`'s return type is a superset of the old one.
- **Data retention/deletion impact:**
  - The three fields live and die with their `access_logs` row. `clearAccessLogs` and any future access-log retention job remove them. They add no biometric data.
  - They reference NVR footage, which the NVR keeps for about 8 days. After that, `capturedAt` and `recordingChannel` point at footage that no longer exists, and the recording route already answers 404 `RECORDING_NOT_FOUND` for those events.
  - Storing a face crop for every face of 60 px or more (owner decision) raises the volume of biometric data in `photoSnapshot`. No retention or deletion policy for access-log images exists yet (open question below).
- **Deployment/restart required:** yes, a rebuild plus restart is needed for the migration to run. Not done, and not requested.

## Proposed server.ts changes (for INT)

1. **`RecognitionOutcomeInput` (server.ts ~3882): add server-owned trace inputs.**
   ```ts
   /** Capture time of the decided frame (Frame.capturedAtMs). Server-owned: never from a request body. */
   capturedAtMs?: number;
   /** TrackOutcome.trackId of the new pipeline. Server-owned. */
   trackId?: string;
   ```
   The pipeline wiring sets them from `TrackOutcome.best.frame.capturedAtMs` and `TrackOutcome.trackId`. The legacy watcher may set `capturedAtMs` from its own grab time. `/api/recognize-face` and device ingest must not copy them from the payload.

2. **Both `AccessLogRecord` literals in `applyRecognitionOutcome` (GRANTED ~4151, DENIED ~4237): add**
   ```ts
   capturedAt: input.capturedAtMs ? new Date(input.capturedAtMs).toISOString() : undefined,
   trackId: input.trackId,
   recordingChannel: recordingConfig?.channels[actionType] ?? undefined,
   ```
   `recordingConfig` is declared at ~6459, after this function. That is fine at runtime, but moving the declaration above `applyRecognitionOutcome` avoids a temporal-dead-zone trap if anything ever records during module initialisation.

3. **Await the durable write (server.ts 4169 and 4255):**
   ```ts
   const persisted = await db.saveAccessLog(accessLog);
   if (!persisted) { summary.persistFailed = true; console.error(`[AccessLog] ${accessLog.id} was not stored in the authoritative database`); }
   ```
   Keep the door decision and order as they are, because the unlock already happens before the write. This closes the read-after-write race for every reader, including other processes. The db-side wait in `057b559` covers only this process.

4. **`GET /api/logs/:id/recording` (server.ts ~6495 and ~6512):** use the exact frame time and the channel recorded at event time.
   ```ts
   const capturedMs = log.capturedAt ? Date.parse(log.capturedAt) : NaN;
   const eventMs = Number.isFinite(capturedMs) ? capturedMs : Date.parse(log.timestamp);
   const win = recordingWindow(eventMs, Date.now());
   // ...
   const storedChannel = log.recordingChannel && /^[0-9]{1,5}$/.test(log.recordingChannel) ? log.recordingChannel : null;
   const channel = storedChannel ?? recordingConfig.channels[gate];
   ```
   Also add the time source (`capturedAt` or `timestamp`) to the `[Recording]` audit line. The recording feature's owner could export the channel validator from `recording.ts` instead of repeating the regex. Once `capturedAt` is the anchor, the `DEFAULT_RECORDING_WINDOW.beforeMs` padding, which also compensated for the 1-2 s write lag, can be revisited.

5. **Frontend/API:** no route change is needed. The fields flow through `publicAccessLog` automatically. The UI may show `capturedAt` (and use `trackId` to group) once it is present.

## Risks and follow-up

- **Known risks:**
  - Read-your-writes wait: a read may wait up to 2 s while PostgreSQL is slow and inserts are in flight. Before, it would have returned stale data immediately.
  - Only this process's writes are covered. Proposal 3 is the complete fix.
- **Observed, not changed:**
  - `reassignEmployeeReferences` runs `UPDATE access_logs SET "employeeId"...` on historical events. That rewrites history, contrary to the immutability rule.
  - In PostgreSQL mode, `saveAccessLog` also mirrors into SQLite, so the local store is a simultaneous secondary copy rather than a strictly explicit fallback mode.
  - Both need separate tasks.
- **Unresolved questions:**
  - Retention and deletion policy for per-face crops in `photoSnapshot` (owner decision).
  - Whether the recording route should prefer the stored channel over the current configuration, which is what is proposed.
- **Dependencies on other agents/commits:**
  - TRK provides `trackId` (it must match `^[A-Za-z0-9][A-Za-z0-9._:-]{0,63}$`; anything else is stored as NULL).
  - STR provides `Frame.capturedAtMs`.
  - INT wires proposals 1-4.
- **Requested integration action/order:** merge `feat/rt-dat` first (additive schema), then STR/PERF/TRK, then INT wiring with the proposals above. When integrating, run the integration suite with `PERSISTENCE_PG_URL` on the throwaway PostgreSQL so the persistence cases run.
