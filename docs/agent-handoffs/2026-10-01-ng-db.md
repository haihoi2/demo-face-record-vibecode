# Agent handoff: N gates wave - persistence (db.ts)

## Task

- **Title:** Gate ids on access events and stranger faces, the `AccessLogQuery.gateId` filter, lock state per door, and
  gate-id normalisation of shadow results. Covers PostgreSQL, native SQLite and the JSON fallback with the same
  semantics (plan `docs/plans/2026-09-29-scale-and-accuracy.md` Part E and section 11; contract `src/server/gates.ts`,
  unchanged).
- **Owner/agent:** data-migrations (single writer of `src/server/db.ts` this wave).
- **Acceptance criteria:**
  1. `access_logs."gateId" VARCHAR(32) NULL` plus an index for the gate filter. `saveAccessLog` stores `gateId` when
     `isGateId()`, otherwise NULL. No backfill. Every read path returns `gateId` (stored, or derived with
     `gateIdForLegacyRow()`).
  2. `AccessLogQuery.gateId`: rows with that id, plus NULL-gateId rows whose `type` maps to it, but only for
     `entry`/`exit`. The `type` filter is unchanged. Keyset paging, counts, stats and CSV follow the filter.
     Stats gain per-gate counts.
  3. `stranger_faces."gateId" VARCHAR(32) NULL`. Writers pass it as an optional extra property (validated). Reads return
     it, or a value derived from `gate`.
  4. `door_lock_states` with `getDoorLockState(doorId, fallback)`, `saveDoorLockState(doorId, state)` and
     `listDoorLockStates()`. `smart_lock_state` is door `main`: it is read when there is no door row, and it is written
     together with door `main`. `doorId` is validated with `isDoorId`.
  5. Shadow results: the legacy `ENTRY`/`EXIT` values read as `entry`/`exit` in pages and summaries. The gate filter
     matches both spellings.
  6. Tests on JSON, SQLite and PostgreSQL (throwaway `postgres:18-alpine`): round trip, derived legacy rows, the filter
     with paging, door states including `main` read and write-through, shadow normalisation, migration from the
     previous release, and rollback.
- **Scope explicitly excluded:** `server.ts`, `src/types.ts`, `src/server/gates.ts`, `src/server/strangerFaces.ts`,
  `auth.ts`, pipeline and frontend files. The changes they need are under "Requested integration action".

## Changes

- **Files changed:** `src/server/db.ts`, `init-db.sql`, the three new test files, the seven predecessor tests and
  fixtures listed above, and this handoff.
- **Behavior changed:**
  - **Access events.** `AccessLogRecord.gateId?: string`. `saveAccessLog` stores it when it matches `GATE_ID_RE`.
    Any other non-empty value is stored as NULL and logged by field name next to the trace fields; the event itself is
    never refused. Replays by id are still no-ops (first write wins, gate included). Every read derives
    `gateIdForLegacyRow()` for NULL rows: `queryAccessLogs`, `getAccessLogsPage`, `getAccessLogs` (startup
    hydration), `getAccessLogMetaById` (`AccessLogMeta` gains `gateId`), `getAccessLogById` (SQLite/JSON),
    `getStrangerCandidateLogsPage`/`ById`. The PostgreSQL `getAccessLogById` loads only id + image, so it carries no
    `gateId`, as before for `type`. Nothing is ever written back: the startup seed of an empty PostgreSQL from the
    local store copies the stored value (NULL stays NULL), and PostgreSQL to local copies the raw column.
  - **Gate filter.** `AccessLogQuery.gateId` uses the same mapping as the reader:
    `("gateId" = $id OR ("gateId" IS NULL AND upper(type) <> 'EXIT'))` for `entry`,
    `... upper(type) = 'EXIT'` for `exit`, and `"gateId" = $id` for any other id. A value that is not a gate id matches
    no rows (`FALSE`), so a malformed parameter never widens to "all gates". It combines with `type`, `status`, `q`,
    `from`/`to` and the keyset cursor, and `total` counts the filtered rows. Because the CSV export pages through
    `queryAccessLogs`, it follows the filter as soon as INT passes the parameter.
  - **Stats.** `AccessLogStats.byGate: Array<{ gateId, total, granted, denied }>` uses derived ids for legacy rows and
    is sorted bytewise. The per-direction `entries`/`exits`/`byHour` fields are unchanged. PostgreSQL computes it with
    one extra `GROUP BY COALESCE("gateId", CASE ...)` query; SQLite and JSON compute it in `accumulateStats`.
  - **Stranger faces.** `normalizeStrangerFace` accepts an optional `gateId`. Exported type:
    `StrangerFaceRecordWithGate = StrangerFaceRecord & { gateId?: string }`. A valid id is stored. Anything else is
    stored as NULL and is never fatal, because the face already carries `gate`. Every read (`ByIds`, `ByLogIds`, page,
    observations) returns `gateId` (stored, or derived from `gate`). The JSON store writes `gateId` only when one was
    stored. Purge tombstones keep it as provenance.
  - **Door lock states.** `getDoorLockState(doorId, fallback)` is synchronous and reads from memory.
    `saveDoorLockState(doorId, state): Promise<boolean>` resolves once the authority has the state.
    `listDoorLockStates()` returns every stored door, sorted. New: `deleteDoorLockState(doorId): Promise<boolean>`
    removes an orphan state after a door is removed; `main` cannot be deleted. `normalizeDoorLockState` (exported):
    - Refuses an invalid `doorId`, `lockId` (printable, at most 64 characters), `state` enum, `isLocked` boolean or
      `status` enum.
    - Cuts descriptive text to the legacy columns (255/64).
    - Non-finite numbers read as 0.
    - Keeps only the known fields, so a token or URL in the body is never stored. `doorId` is the key.
    - Door `main` with no door row reads `smart_lock_state`. If both exist, the newer `lastActionAt` wins and a tie goes
      to the door row. So if the previous image writes the legacy row after a rollback, rolling forward again shows its
      state.
    - Saving `main` upserts both rows in ONE transaction: `BEGIN IMMEDIATE` on SQLite, a single staged file write on
      JSON. The partial-failure test shows a refused legacy write rolls the door row back and the call returns `false`.
    - All lock writes, including the legacy `saveSmartLockState` PostgreSQL write, run in call order on one queue, so
      the stored state is the last state saved. 8 concurrent saves were tested.
    - Memory is loaded from the local store at startup. When PostgreSQL becomes active, its rows replace memory. Doors
      saved by this process and doors that only the local store knows (first run on PostgreSQL) are written up.
    - Writes go through to the local store, like the legacy lock row.
  - **Shadow results.** `shadowGateId()` (exported) maps exactly `ENTRY`→`entry` and `EXIT`→`exit`.
    - New rows are stored with the id, even if a writer still passes the direction.
    - Old rows are not rewritten.
    - Page rows, summaries and the gate filter use the id. A filter for `entry`/`ENTRY` matches both spellings
      (`gate = ANY(...)`, `IN (?, ?)`).
    - Summary counts and latency samples of both spellings merge into one row.
  - **Startup ordering (PostgreSQL).** PostgreSQL becomes the active store just before its migration runs. Access-log
    and lock writes now wait for the migration to finish (`pgSchemaSettled`), because on the first boot after an upgrade
    an INSERT naming `"gateId"` would otherwise fail until the `ALTER` had run. Reads already waited for in-flight
    writes, so this only matters at boot.
  - **Fix (pre-existing, JSON fallback only).** `getAccessLogs` returned the store's live array. `server.ts` unshifts a
    new event into that array before calling `saveAccessLog`, so the "already stored" check skipped the disk write;
    events reached disk only with the next unrelated save. The function now returns copies (with the derived
    `gateId`), and the event is written. There is a regression test.
- **API/event contracts added or changed:** none at HTTP level (INT owns the routes). Store level:
  - Added: `AccessLogRecord.gateId`, `AccessLogQuery.gateId`, `AccessLogMeta.gateId`, `AccessLogStats.byGate` /
    `AccessLogGateCount`, `SmartLockStateRecord.doorId`, `StrangerFaceRecordWithGate`, `getDoorLockState`,
    `saveDoorLockState`, `listDoorLockStates`, `deleteDoorLockState`, `normalizeDoorLockState`, `shadowGateId`.
  - Changed: shadow `gate` values read lowercase for the two legacy gates.
- **Schema/migration changed:** yes, additive. See Data and deployment.
- **Environment/configuration changed:** none.
- **Security/privacy impact:**
  - No new biometric data. `stranger_faces."gateId"` is a slug that follows the existing retention and tombstone.
  - `door_lock_states` holds display and relock-timer state only. It authorises nothing, and the store drops unknown
    fields so a door-controller token cannot ride into it. Tests assert this on all three stores.
  - The gate filter fails closed: a malformed id returns no rows.

## Data and deployment

- **Forward migration:** automatic at startup, additive, no backfill.
  - PostgreSQL main batch: `ALTER TABLE access_logs ADD COLUMN IF NOT EXISTS "gateId" VARCHAR(32)` (nullable, no
    default, so a catalog-only change with no table rewrite), then
    `CREATE INDEX IF NOT EXISTS idx_access_logs_gate_ts ON access_logs ("gateId", "timestamp" DESC, id DESC)`.
    `PG_STRANGER_FACES_DDL` adds `stranger_faces."gateId" VARCHAR(32)`. `PG_DOOR_LOCK_STATES_DDL` runs as its own
    statement with its own ready flag, so a failure there only refuses lock writes to PostgreSQL. It creates
    `door_lock_states ("doorId" VARCHAR(32) PK CHECK (~ DOOR_ID_RE), state JSONB NOT NULL, "updatedAt" VARCHAR(64) NOT NULL)`.
    `init-db.sql` has the same DDL for new databases.
  - **Index build:** it is a plain `CREATE INDEX` (as `idx_access_logs_ts_id` was), so it blocks writes to
    `access_logs` while it builds once. Writes wait for it and are not lost, but a large table means a longer pause on
    the first boot. I did not query the live database. If the owner wants zero write pause, run
    `CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_access_logs_gate_ts ON access_logs ("gateId", "timestamp" DESC, id DESC);`
    by hand before deploying; the startup statement is then a no-op.
  - SQLite: the same columns go at the end through `ALTER TABLE ... ADD COLUMN` (the duplicate-column error means the
    migration already ran). The index is created after the column exists. `door_lock_states` uses a length CHECK.
  - JSON: new optional key `door_lock_states`. Old records without `gateId` are read as derived values.
- **Rollback or compensation:**
  - Going back to the previous image needs no DDL; this was tested on PostgreSQL and SQLite. Old code never names
    `"gateId"` or `door_lock_states`. Its explicit INSERTs leave the columns NULL and its SELECTs ignore them.
    `smart_lock_state` keeps door `main`'s current state, because every save of `main` writes it.
  - Lost while rolled back: the gate of events at gates other than entry/exit. The rows stay, and the old UI reads them
    by `type`. Lock states of doors other than `main` are also lost; those doors relock on their own timer.
  - Shadow rows written by this release say `entry`/`exit`. An old summary groups by the raw value, so it could show
    `entry` next to `ENTRY`. Optional compensation (this is comparison data, not access history):
    `UPDATE pipeline_shadow_results SET gate = upper(gate) WHERE gate IN ('entry','exit');`
  - Full DDL rollback (not recommended; it loses the gate of non-legacy events): `DROP TABLE door_lock_states;`
    `DROP INDEX idx_access_logs_gate_ts;` `ALTER TABLE access_logs DROP COLUMN "gateId";`
    `ALTER TABLE stranger_faces DROP COLUMN "gateId";`. A restart re-applies everything (tested).
- **Backward compatibility:** old rows and old writers keep working. Store callers that pass no `gateId` get exactly
  what they got before, plus a derived `gateId` field on reads. `getSmartLockState` and `saveSmartLockState` are
  unchanged for callers and stay consistent with door `main`.
- **Data retention/deletion impact:** no new biometric fields and no change to purge. Access history stays immutable
  (no rewrite). `door_lock_states` is non-biometric runtime state; `deleteDoorLockState` cleans it up when a door is
  removed.
- **Deployment/restart required:** yes, a rebuild and restart, but only together with INT's `server.ts` (nothing
  calls the new methods yet). Do not deploy this branch alone.

## Risks and follow-up

- **Known risks:**
  - The first boot on a large `access_logs` table pauses writes while the index builds (see above).
  - Lock-state ordering assumes one gateway process per database, which is the current topology.
  - Door `main` compares `lastActionAt` ISO strings. Both releases write `toISOString()`, so they compare correctly.
  - Root disk: the host was at 84-85% before this task and went past 85% during the gates because of other workloads
    (`/tmp` is tmpfs). My image (1.84 GB unique) was removed right after the gates, and `docker builder prune -f` was
    run. After cleanup the disk was at 87.2% with nothing of mine left on it. The owner should look at the
    other workloads.
- **Unresolved questions:**
  1. Should `AccessLogStats.byGate` also carry `entries`/`exits` per gate? It is cheap to add if the dashboard wants
     it.
  2. Should the stats `byGate` include configured gates that have zero events? db.ts does not know the
     configuration, so INT would merge them.
- **Dependencies on other agents/commits:** none for this commit. INT needs this branch for the routes below.
- **Requested integration action/order:** merge `feat/ng-db` before or with INT. Proposed changes for the owners:

     "Gate id (N gates); absent on faces from before gate ids: readers derive it from `gate`". Then
