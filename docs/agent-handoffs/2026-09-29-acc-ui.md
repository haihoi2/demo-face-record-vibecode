# Agent handoff

## Task

- **Title:** Accuracy wave, frontend (plan `docs/plans/2026-09-29-scale-and-accuracy.md`, Parts B and C, section 9 "Contract").
- **Owner/agent:** acc-ui (frontend).
- **Acceptance criteria:**
  1. `RealtimeEngineCard` shows a per-gate "Độ chính xác (24 giờ)" section fed by `GET /api/pipeline/shadow-summary?hours=24`: decisions, employees/strangers/insufficient, the share of tracks with no usable face (`framesUsedZero/decisions`) as the throughput indicator, and the agreement breakdown (agree / shadow-only / legacy-only / identity-mismatch / none) with identity mismatch highlighted "cần kiểm tra". HTTP 404 (older server) hides the section; an empty window is stated. Refreshes on the card's existing 5 s cadence.
  2. `EmployeeRegistration` shows per-camera coverage per employee from the `coverage` array of `GET /api/employees/:id/templates`, derived from `templates`/`byStream` when `coverage` is absent; a compact indicator per camera ("thiếu mẫu ở Cổng ra" style) in the employee list; a filter "Thiếu mẫu trên camera…". Adaptation templates (`source: "adaptation"`) are listed like the others with a "tự động" tag and the existing delete button.
  3. `StrangerClusterModal` shows a cluster's `suggestion` as "Có thể là <name> (<code>) – <cosine %> – chưa có mẫu ở <cameras>" on the group card and in the resolve panel, with a one-click "Gộp vào <name>" that pre-selects the employee in the existing merge flow. The operator confirms; nothing is automatic; never worded as a decision.
  4. Pure-helper and source-inspection tests, >= 8 cases.
- **Scope explicitly excluded:** backend routes and behaviour, `server.ts`, `src/server/**`, `src/types.ts`, `src/App.tsx`, any schema or environment change.

## Risks and follow-up

- **Known risks:**
  - The employee list issues one `GET /api/employees/:id/templates` per employee (31 today, 4 in flight). Acceptable now; with N gates and hundreds of employees a batch endpoint is the right shape (proposal below).
  - `noUsableFaceTone` colours the stat amber at >= 40%, the plan's Part A success line. It is a display hint with the constant in one place (`NO_USABLE_FACE_WARN_SHARE`); it is not a policy the UI enforces.
  - The suggestion pre-fills the merge form with a placeholder `Employee` (name, code, id) until the roster search answers. If the employee was deleted in between, the merge request is refused by the server (404) and the existing error alert shows; nothing is done client-side.
  - Source-inspection tests pin a few code shapes in the three components (`Promise.all([...watch..., fetchShadowSummary()])`, `readSuggestion(cluster.suggestion)`, `setFormMode("MERGE"); setMergeTarget(suggestionAsEmployee(suggestion));`). Refactors that change them must update `tests/accuracyUi.test.ts`.
- **Unresolved questions / what the backend must provide beyond the contract text:**
  1. `ShadowAccuracySummaryView.gate` is matched case-insensitively against `ENTRY`/`EXIT` (`gateKeyOf`). Any other spelling (a slug like `side`) is ignored by the two-gate card until Part E.
  2. `since` per gate or at the top level: the card shows the gate's `since`, falling back to the body's. Either alone is fine.
  3. `coverage[].gate` is stored but not used for matching; cameras are matched by `streamId` against the configured streams (`/api/camera-streams/config`, ids like `exit-501`). The `streamId` values must be the configured stream ids, not labels. Templates with no stream should be reported as `streamId: "unknown"` (or omitted); the UI does not list them as a camera.
  4. `suggestion.missingCameras` is displayed verbatim (joined with ", "). Send human-readable camera or gate names ("Cổng ra"), not stream ids, or the sentence reads "chưa có mẫu ở exit-501".
  5. `suggestion.cosine` is expected in 0..1 (rendered as a rounded percentage, clamped).
  6. Adaptation templates are recognised by `source === "adaptation"` (case-insensitive, trimmed) on the templates body; `DELETE /api/employees/:id/templates/:templateId` must accept them like any other template (the UI reuses the existing button).
- **Proposed hotspot changes (not made):**
  - `src/types.ts` (INT): `FaceTemplate.source` should include `"adaptation"`: `source: "enrollment" | "merge" | "manual" | "auto" | "adaptation";`. The UI compares strings, so nothing breaks today, but the type is currently narrower than the contract.
  - `src/types.ts` (INT, optional): export a `TemplateCoverageEntry { streamId: string; gate: string; count: number; adaptation: number }` and reference it from the templates route response so the client's local `CoverageEntry` in `src/utils/accuracyUi.ts` can be replaced by the shared type.
  - `server.ts` (INT, follow-up, not needed for this wave): `GET /api/employees/coverage` (viewer) → `{ success, streams: [{streamId, gate}], employees: [{ employeeId, coverage: [...] }] }` to replace the per-employee reads in the list. The client's `deriveCoverage` already accepts the per-employee shape, so switching is a one-place change.
- **Dependencies on other agents/commits:** the INT agent's routes (`shadow-summary`, `coverage` on the templates body, `suggestion` on cluster payloads) and the db agent's `db.ts` implementation of `getRecognisedFaceObservations` (which also clears the base's typecheck error).
- **Requested integration action/order:** merge after `release/accuracy` `4ccfb4f`, in any order relative to the db and INT branches; the client works against both old and new servers. On the integrated branch rerun typecheck (expected exit 0 once `db.ts` implements the interface), the full unit suite, the build, and the SQLite + PG integration gates.
