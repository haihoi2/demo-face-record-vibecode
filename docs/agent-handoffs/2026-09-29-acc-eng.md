## Changes

- **Files changed:** the files above.
- **Behavior changed:** none by default. `embedFace()` now builds its tensor through `alignedToTensorData()` and runs
  the model through `runRecognizer()`; with `FACE_TTA_FLIP` unset the output is byte-identical to the previous
  inline code (test: compared against a direct `recognizer.run()` on the same session, `Buffer.equals`). With
  `FACE_TTA_FLIP=1` (or `true`), `embedFace()` returns `l2(l2(f(x)) + l2(f(flip(x))))` - two recogniser runs,
  fail-closed to `null` if either fails. `flipHorizontal()`, `alignedToTensorData()`, `ttaFlipEnabled()` are
  exported pure helpers. `getFaceEngineInfo()` gains `ttaFlip: boolean` (additive field; no consumer asserts the
  exact key set).
- **API/event contracts added or changed:** none. `/api/face-engine/status` `info` carries the extra `ttaFlip`
  field automatically (additive).
- **Schema/migration changed:** none.
- **Environment/configuration changed:**

  | Variable | Default | Effect |
  |---|---|---|
  | `FACE_TTA_FLIP` | unset = off | `1`/`true` (case/whitespace-insensitive) enables flip TTA in every process that embeds (legacy engine, face workers, pipeline workers all go through `embedFace()`); any other value = off, so a typo cannot enable it |

  Not added to `.env.example`/compose (not my files) and not recommended until measured - see D2 below.

## Results

### D2 - horizontal-flip TTA

**Latency cost (measured; models only, synthetic 112x112 crops, no biometric data).** `onnxruntime-node` 1.30, CPU
EP, graph optimisation `all`, container `--cpus 2` under `nice -n 15`, host load 10-12 (shared host: absolutes are
inflated, ratios are the robust part), median of 30 timed calls after 5 warm-ups
(scratch `bench-flip.cjs`, deleted).

| model | threads | single run (median / p95) | two runs x + flip(x) | batch of 2 [x, flip(x)] |
|---|---|---|---|---|
| r50 (FP32, batch dim dynamic) | 2 | 363 / 447 ms | 747 / 925 ms (**x2.05**) | 732 / 826 ms (x2.01; ORT warns "expected shape {1,512} got {2,512}" every call) |
| r50 | 1 | 694 / 765 ms | 1381 / 1520 ms (x1.99) | 1396 / 1525 ms (x2.01) |
| r50_int8 (batch dim static 1) | 2 | 101 / 125 ms | 203 / 234 ms (**x2.01**) | not possible (static batch) |
| r50_int8 | 1 | 161 / 192 ms | 324 / 367 ms (x2.01) | not possible |

Reading: flip TTA doubles the recogniser cost exactly; batching the two views saves nothing on the CPU EP and the
INT8 graph cannot take it, so the implementation is two sequential runs (works for every recogniser file). In the
sizing table of the rt-calib handoff this turns the recogniser term from 0.6-1.9 into 1.2-3.8 cores for two gates
at 4 fps with r50_int8, and from 5.4 into 10.9 cores worst case with FP32 r50.

### Adaptation policy floors (Part C3) - what the surviving aggregates support

Policy at `acceptSingle 0.55`: fused cosine >= 0.65, margin >= 0.15, quality >= 0.35, 5 per camera, novelty 0.05.
Source: r50 aggregates of the rt-calib report (378 scored crops, EMP-0465 excluded; pairwise sets, and the
"templates per person" analysis where the gallery is the k best-quality crops per employee and every other crop is a
probe scored by max cosine over the gallery - the same score `matchObservations` uses). Percentile-interpolated
values are marked "est.".

| set | n | p50 | p95 | max | >= 0.65 (the adaptation cosine floor) | >= 0.55 (a grant) |
|---|---|---|---|---|---|---|
| strict impostor pairs (two employee ids) | 5,503 | 0.016 | 0.128 | **0.455** | **0 pairs** (max 0.195 below the floor) | 0 (0.00 %) |
| strict impostor, best-of-5-template gallery | 290 | 0.076 | 0.149 | **0.283** | **0** | 0 |
| strict impostor, best-of-10-template gallery | 290 | 0.091 | 0.252 | 0.455 | **0** | 0 |
| probable impostor (employee vs DENIED crop), 5-template gallery | 693 | 0.084 | 0.367 | 0.670 | at most a few (< 5 %, max 0.670; CALIB traced this tail to EMP-7602 denied as a stranger, i.e. label noise, not a face match) | 0.72 % |
| genuine, best-of-5-template gallery | 118 | 0.614 | 0.803 | 1 | **~41 % est.** | 57.6 % (measured) |
| genuine, best-of-10-template gallery | 103 | 0.652 | 0.881 | 1 | **~50 % est.** | 70.9 % (measured) |
| genuine ENTRY-ENTRY pairs (single template) | 3,895 | 0.580 | 0.845 | 1 | ~38 % est. | 51.3 % (all genuine, measured) |
| genuine EXIT-EXIT pairs (single template; EMP-8922's exit label is two faces) | 213 | 0.225 | 0.573 | 1 | < 5 % | < 5 % |
| genuine CROSS-gate pairs (entry template vs exit probe and vice versa) | 259 | 0.084 | 0.523 | **0.600** | **0 pairs** | < 5 % |

Readings, stated as bounds:
- **Impostor pass rate at the floors: 0 of 5,503 strict pairs and 0 of 290/290 gallery probes** at the cosine floor
  alone; the margin floor (>= 0.15) can only lower it. The strict tail sits 0.19 (pairwise) to 0.37 (5-template
  gallery) below the floor. The only scores above 0.65 on the whole set are probable-impostor pairs whose "impostor"
  is most likely the same person denied (label noise). The floor is safe on this data; it is not the binding
  constraint.
- **Genuine grants that would qualify (entry camera, where templates exist): roughly 70 % of grants** (est. 41 %
  of probes qualify vs 57.6 % granted with a 5-template gallery; margin rarely binds because the runner-up's best
  cosine is p95 0.149, and quality rarely binds because capture quality is p5 0.62 on this set). So the job fills a
  camera's 5 slots within a handful of grants once ANY template exists on that camera.
- **Seeding camera B from camera-A templates does not start on this site.** The cross-gate genuine maximum is
  0.600 < 0.65 and the p95 is 0.523 < 0.55: with entry-only templates fewer than 5 % of exit passages are even
  granted, and none of the granted ones reaches the adaptation floor. (A 5-template entry gallery raises the max
  over templates somewhat, but the pairwise max is 0.60, so reaching 0.65 would be rare at best; the replay in
  `adapt-sim.ts` Part 2 measures this exactly when the data exists.) The plan's C3 sentence "the first confident
  matches seed that camera's templates" therefore holds only once camera B has at least one template from C1
  (operator merges the stranger group into the employee -> template from that camera's crop) or from enrolment;
  after that, adaptation grows the camera from 1 to 5 templates within roughly 1-2 grants per slot (70 % of grants
  qualify). **Adaptation is a growth mechanism, not a seeding mechanism, on this site**: the exit camera's 23 %
  exit-to-exit TAR and the cross-camera gap are a camera-placement/enrolment question (D5, C1), as the plan says.
- Trade-off around the floor: lowering `minCosineAboveAcceptSingle` from 0.10 to 0.05 (floor 0.60) leaves 0.145
  above the strict max but does not make cross-gate seeding possible either (cross-gate max 0.600 - a single pair);
  raising it to 0.15 (floor 0.70) costs roughly 12 points of the genuine qualify rate (est.) for no measurable
  impostor benefit. **Keep 0.10.**

### Proposed change to the policy contract (for the contract owner; not applied)

The floors are right. The gap the tests exposed is **diversity, not safety**: `planAdaptation` treats two crops as
distinct when their cosine is < 0.95 (`minNovelty 0.05`), and consecutive frames of ONE passage typically sit at
0.85-0.95. One good passage can therefore fill all 5 slots of a camera with near-identical crops from one minute,
which is exactly the k=2 dip the rt-calib handoff describes ("two best-quality crops from one day; quality alone is
a poor selector, which is why the planner also spreads over cameras and dates") - `planGalleryDerivation` spreads
over dates, `planAdaptation` does not. Proposal (deterministic, cheap, testable):

```ts
// galleryAdaptation.ts (contract owner)
export interface ExistingTemplate { /* ... */ sourceLogId?: string; capturedAt?: string; }
export interface AdaptationPolicy { /* ... */
  /** At most one adaptation template per access event per camera (default true). */
  onePerEvent: boolean;
  /** Prefer days the camera has no template for: an observation from a day already covered is taken only if no other day is waiting (default true). */
  spreadOverDays: boolean;
}
```
In `planAdaptation`: skip an observation whose `logId` equals an existing/planned template's `sourceLogId` on that
camera; when several observations are eligible for one camera, order by (new day first, quality desc, newest)
instead of (quality desc, newest). `server.ts` already passes `sourceLogId`/`capturedAt` when saving, so the
writer needs no change beyond mapping the two fields into `existing`. Alternatively, raise `minNovelty` to 0.10
(cosine < 0.90) as a stop-gap - but same-passage frames straddle 0.90, so the event rule is the reliable one.
