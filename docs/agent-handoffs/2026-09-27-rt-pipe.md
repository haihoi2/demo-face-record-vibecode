# Agent handoff: PIPE - F11 (pipeline inference off the main thread), F12 (reader transition log)

## Task

- **Title:** Fix rc1 blocker F11 and retest against the MT bar.
  - Move the real-time pipeline's SCRFD/ArcFace work off the Node main thread.
  - Make the StreamReader stale watchdog immune to event-loop lag.
  - Log reader transitions (F12).
- **Owner/agent:** PIPE. For this task PIPE is the backend integrator and the only writer of:
  - the `server.ts` pipeline block;
  - `src/server/pipeline/**`.
- **Acceptance criteria (from the brief):**
  1. A `worker_threads` worker per gate. The worker owns:
     - engine loading, with the same FACE_* configuration as the main engine;
     - detection, alignment, quality and clear-face checks;
     - the GateTrackSession, embeddings and tick housekeeping.

     The host posts only the newest frame, and only when the worker is idle. The buffer is transferred, never
     queued, and dropped frames are counted. Results come back without pixels; a crop is included only on request.
     Stats and errors come back too. The context is pushed on start and on change, and the pipeline fails closed.
     A worker crash is logged, restarted with back-off and surfaced. `stop()` terminates cleanly. The public shape
     stays the same.
  2. The watchdog does not misfire under event-loop lag. A real stall is still detected within ~1-2 s, and a lag
     test covers this.
  3. F12: each reconnect or stale transition is logged once, without the host, and rate-limited.
  4. Unit tests cover the host/worker protocol with fakes, and the 8 GatePipeline behaviours stay covered.
  5. Gates: typecheck, unit, build, and integration on SQLite and PostgreSQL.
  6. Retest with the MT replay harness against the bar. Try the entry gate area and INT8 as variants.
- **Scope explicitly excluded:**
  - `faceEmbedding.ts` semantics, `faceFusion.ts`, `db.ts`, `types.ts` and `contracts.ts` are unchanged.
  - Crops-only storage for `live` is still open (see the MT sign-off).

## Changes

- **Files changed:**
  - `server.ts`
  - `package.json`
  - `src/server/pipeline/gatePipeline.ts`: rewritten as the host
  - `src/server/pipeline/streamReader.ts`
  - new `src/server/pipeline/pipelineProtocol.ts`, `pipelineCore.ts`, `pipelineWorker.ts`, `onnxEngine.ts`
  - `tests/gatePipeline.test.ts`
  - `tests/streamReader.test.ts`
  - new `tests/pipelineHost.test.ts`, `tests/pipelineWorker.test.ts`, `tests/fixtures/blockingPipelineWorker.ts`
- **Behavior changed:**
  - **Split into host and worker.** `GatePipeline` is now a host on the main thread: stream reader, motion gate,
    context and reporting. Each gate also has a worker thread (`pipelineWorker.ts` runs `pipelineCore.ts`) that owns
    everything ONNX: engine loading, SCRFD, align/quality/clear, GateTrackSession, ArcFace, tick housekeeping, and
    optional crops via `faceCrop`.
  - **Frame hand-off.** The host sends the newest frame only when the worker has answered the previous one. The RGB
    buffer is transferred (zero-copy; a pooled/shared buffer is copied first). Frames that arrive meanwhile are
    superseded and counted in `framesDroppedBusy`.
  - **Fail closed on both sides.** Without a context from `pipelineContext()`, no frame is sent
    (`framesSkippedNoContext`). The worker also refuses to decide unless its own engine is loaded with the same model
    tag.
  - **Context.** The context is fingerprinted: gallery ids, template values, tags, thresholds and readiness. It is
    pushed on start and whenever the fingerprint changes (checked every 5 s).
  - **Worker failures.** Crash, exit or hang (no answer for 20 s) leads to a log line, a restart with back-off
    (1 s doubling to 30 s, reset after 60 s healthy) and entries in `stats().lastError` / `stats().worker`. Open tracks
    of a dead worker are lost; no outcome is invented for them.
  - **`stop()`.** The worker closes open tracks and reports them, then answers `stopped` and is terminated (after
    3 s at most).
  - **Worker priority.** The worker lowers its own priority before loading the engine (`PIPELINE_WORKER_NICE`,
    default 10). ONNX Runtime's pool threads inherit it (verified: all threads the worker creates show nice 10, the
    main thread 0). FFmpeg, HTTP and the legacy watcher therefore win when CPU is short.
  - **Stale watchdog.**
    - Staleness is measured on bytes read from the pipe, not only on complete frames.
    - A tick that fires more than `staleMs/2` late sets an I/O checkpoint (`setImmediate`, which runs after the poll
      phase that reads the pipe). No verdict is taken until the checkpoint has passed.
    - Under continuous lag, a verdict is still taken at least every `4 x staleMs`.
    - A frozen stream is still declared stale on the next on-time tick after the checkpoint (~1.25 s).
  - **F12 log lines.** One line per stale/lost/failed-to-reconnect event and one per recovery, e.g.
    `[Pipeline EXIT] stream failed (ffmpeg exited (code 8) (404 not found)); reconnect 6 in 30 s`.
    - The reason is reduced to a keyword. No URL, IP, login or verbatim stderr appears.
    - Failures and recoveries are rate-limited separately: one line per 10 s, with suppressed lines counted.
  - **server.ts.**
    - Drops the main-thread `pipelineEngine` binding and passes `log` to the reader.
    - Rate-limits pipeline error lines (1 per 10 s per gate).
    - Logs one counters line per gate per minute (`PIPELINE_STATS_LOG_MS`, 0 = off). The line carries status, fps,
      reconnects, processed/still/dropped/no-context frames, detections, embeddings, loop time, decisions, contextOk
      and worker state. It contains no ids and no URLs.
- **API/event contracts added or changed:**
  - `pipeline_shadow_result` SSE and the watcher runtime are unchanged. `pipelineStats` still sends the same fields.
  - `GatePipeline.stats()` gains `framesDroppedBusy`, `framesSkippedNoContext` and
    `worker {state, restarts, engineReady, modelTag, openTracks}`. These are internal and not in `types.ts`; see
    proposal P3.
  - `GatePipelineOptions` loses `engine`, `idleWaitMs` and `tickMs` as a host timer. It gains `createWorker`, `crops`,
    `statsMs`, `frameTimeoutMs`, `restartBackoff*` and `stopTimeoutMs`.
  - In results the host receives, `best.frame.rgb` is empty and pixels stay in the worker; use `best.crop`.
  - `StreamReaderOptions` gains `log` and `logIntervalMs`.
- **Schema/migration changed:** none
- **Environment/configuration changed (all optional):**

  | Variable | Default | Effect |
  |---|---|---|
  | `PIPELINE_WORKER_NICE` | 10 | worker thread priority (0-19; 0 = unchanged) |
  | `PIPELINE_ORT_THREADS` | inherit `FACE_ORT_THREADS` | ORT intra-op threads, pipeline workers only |
  | `PIPELINE_DETECTOR_VARIANT` | inherit `FACE_DETECTOR_VARIANT` | `fp32`/`int8`, pipeline workers only |
  | `PIPELINE_DETECT_SIZE` | inherit `FACE_DETECT_SIZE` | pipeline workers only; ignored with INT8 (fixed 640) |
  | `PIPELINE_STATS_LOG_MS` | 60000 | stats line period (0 = off) |
  | `PIPELINE_WORKER_PATH` | resolved | worker entry override (strict) |

  None of these is in `docker-compose.yml` yet (proposal P2).
- **Build:** `npm run build` now also emits `dist/pipelineWorker.cjs` via esbuild, like `faceWorker.cjs`.
  - Dev (`tsx server.ts`) runs `src/server/pipeline/pipelineWorker.ts` through the inherited tsx loader.
  - The bundled worker was verified with the real models: engine ready, tag `arcface_w600k_r50`, ~0.5 s per
    1080p frame (FP32, 2 cores).
- **Security/privacy impact:**
  - Shadow still never unlocks, writes no access log and stores no image. `crops: false` in shadow, and the worker
    does not create crops unless asked.
  - Embeddings and pixels stay backend-side, between threads of one process.
  - Log lines are host-free; the stats line carries counters only.
  - Fail-closed is unchanged or stricter: the host checks the context and the worker checks its own engine and tag.

### What the numbers say

1. **The rc1 failure mode is fixed.**
   - A worker thread that blocks 300 ms per frame leaves main-thread timer lag under 150 ms (unit test with a real
     thread).
   - In the final both-gates run the event loop was late 213 times and not one of them produced a stale verdict. The
     remaining disconnects are RTSP sessions ended by the server side (`ffmpeg exited (code 0)`). Most likely MediaMTX
     dropped readers whose decoders fell behind for lack of CPU; these are not watchdog verdicts.
   - During the EXIT-only run, the event loop was late 34 times (legacy ONNX still runs on the main thread). None of
     those became a false stale: 0 reconnects in 1000 s of playback, and the reader stayed at 8 fps.
2. **The bar cannot be met in a 2-core container with both gates on, by any change in this scope.**
   - E1 has no inference at all. The two always-open HEVC decoders alone (≈1.56 cores) plus the legacy watcher
     saturate the quota: throttled 86% of periods, `/api/health` p95 1542 ms, legacy scans +24% / +57%.
   - Every both-gates run inherits this, and FFmpeg starvation then produces real stalls and reconnects.
3. **EXIT-only shadow protects the door path at 2 cores.**
   - Health p95 280 ms and legacy scan p50 -3% / -7% pass the bar, with 0 reconnects in playback.
   - Throughput is bounded by the CPU left after decode and legacy: ~0.3 core, ~2-3 fps while people are in view,
     5/36 decided.
4. **The entry gate area as a 3408x456 strip is unusable at detector size 640.**
   - The strip is letterboxed into a 640 square (scale 0.19), so a 60 px face reaches SCRFD at ~11 px: 0 outcomes.
   - MT's `verify-detect640.json` gives the same picture on the full 4K frame: 1/9 entry faces detected at the first
     usable moment, versus 9/9 at 1280.
   - FP32 at 1280 detects them but costs 5.5 s per frame here. INT8 cannot run at 1280.
   - This is a detector-geometry issue (proposal P1), independent of threads.
5. **INT8 vs FP32 (pipeline only).**
   - INT8 cuts detect loop time about 3-4x (X1 vs X2: 1071 -> 279 ms p50) and gives more decisions per minute.
   - 1 ORT thread beats 2 under a quota: no spinning pool, p95 loop 651 vs 1131 ms, fewer throttled periods.
   - ArcFace stays FP32 (PERF: INT8 fails the drift bar) and costs 360-670 ms per embedding. It dominates once faces
     are present.

### Recommendation

- **Configuration for any shadow deploy:**
  - `PIPELINE_DETECTOR_VARIANT=int8` (pipeline only; legacy stays FP32);
  - `PIPELINE_ORT_THREADS=1`;
  - `PIPELINE_WORKER_NICE=10` (default);
  - `CAMERA_ALLOWED_HOSTS` set per the NET handoff.
- **Do not enable both gates in shadow on dev yet.** On the 2-core measurement it fails the legacy/health items from
  decode cost alone. On the real (unquota'd, shared 8-core) host it would add ~1.6 cores of continuous decode plus
  inference.
- **Acceptable now, if the owner wants shadow data:** `PIPELINE_MODE_EXIT=shadow` only. It passes the
  legacy-protection items and has 0 reconnects, but produces decisions for only a minority of persons at 2 cores.
- ENTRY needs P1 first.
- The throughput and coverage items need a CPU budget decision: measure at the real budget (P4) before the owner
  decides.

## Risks and follow-up

- **Known risks:**
  - **CPU is the limit.** See the numbers above. Idle CPU also cannot meet ≤ 0.5 cores while decoding continuously
    (STR already noted this).
  - **Detection geometry of wide gate areas (P1).** The entry gate area as configured cannot produce decisions.
  - **Low processed fps undermines the tracker.** Below ~2 fps, `tentativeMaxMissMs` 500 ms and `confirmHits` 2 let
    tentative tracks expire. Many passages then get no outcome at all, not even "insufficient". TRK should consider
    scaling these with the measured frame interval.
  - **Worker restarts lose open tracks.** No outcome is emitted for them; this is logged.
  - **Silent INT8 detection failures.** INT8 plus `FACE_DETECT_SIZE≠640` (global) makes `detectFaces` fail every
    frame. It is logged but returned as "no face" (F-P1 for PERF). The pipeline override guards its own case.
- **Unresolved questions:**
  - What CPU budget may the gateway use on the shared dev host?
  - Is shadow-on-EXIT-only acceptable as the first step?
- **Dependencies on other agents/commits:** none for merging; P1/P2/P3/P4 below.
- **Requested integration action/order:** INT merges `feat/rt-pipe` into `release/rt-pipeline` after the MT re-run.
  MT re-signs with `run-signoff.sh rc2 --replay`; that runner needs `CAMERA_ALLOWED_HOSTS=mediamtx-<suffix>` on the
  replay gateway.

### Proposals for other owners (not applied)

- **P1 (PERF, `faceEmbedding.ts`): aspect-preserving detection for wide gate areas.**
  - Letterbox a wide area into a non-square SCRFD input, e.g. 1536x224 for 3408x456 (fewer pixels than 640x640; faces
    at ~0.45 scale). Alternatively, tile it.
  - det_10g FP32 accepts dynamic sizes (1280 works). The INT8 export is static 640: re-export it dynamic, or tile.
  - Also make an INT8 + non-640 `FACE_DETECT_SIZE` combination fail loudly at load, not per frame.
- **P2 (INT, `docker-compose.yml` / `.env.example`): pass the new optional variables through.**
  - `PIPELINE_WORKER_NICE`, `PIPELINE_ORT_THREADS`, `PIPELINE_DETECTOR_VARIANT`, `PIPELINE_DETECT_SIZE`,
    `PIPELINE_STATS_LOG_MS`, and `PIPELINE_FPS` (already read by `server.ts`, not in compose).
  - For INT8, mount `/data/models` (PERF proposal 4).
- **P3 (DAT/INT, `types.ts`): add to `GateWatchRuntime.pipelineStats`** so the dashboard and MT can see drops and
  worker health:
  - `framesDroppedBusy?: number`, `framesSkippedStill?: number`, `workerState?: string`, `workerRestarts?: number`.
  - `pipelineRuntime()` in `server.ts` would then forward `st.framesDroppedBusy`, `st.framesSkippedStill`,
    `st.worker.state` and `st.worker.restarts`.
- **P4 (owner/INT): measure the real budget.**
  - Run MT's replay with the gateway at the CPU the dev container really gets (no quota, or a cpuset of 4-6 cores)
    before deciding on a shadow deploy.
  - The brief's `--cpus 2` rule prevented me from running it.
- **P5 (STR/INT, later): move the reader off the main thread as well.** A reader worker could post frames to the
  pipeline worker over a MessageChannel. Legacy ONNX still blocks the main thread for 0.5-2 s. The checkpoint
  watchdog handles this, but the pipe is not drained during those blocks.
