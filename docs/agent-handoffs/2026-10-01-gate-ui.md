# Agent handoff

## Task

- **Title:** Gate UI gaps after the N-gate release (owner request 2026-10-01, "yes for all"): (1) gate on/off switch for admins, (2) lock status for every door.
- **Owner/agent:** frontend agent (gate-ui). Integration owner: Hermes (INT).
- **Acceptance criteria:**
  1. Gate identity section of `CameraStreamConfigPage.tsx` (admin only) has an on/off switch that sends `PUT /api/gates/:gateId { enabled }` through `operatorJsonFetch` (CSRF).
  2. Switching a gate OFF asks first. The dialog says plainly that the gate stops scanning and its door will not open from face recognition while it is off. Switching ON needs no confirmation.
  3. Gate tabs show an "Đang tắt" badge for switched-off gates. Operators and viewers see the state but get no switch. The server's error text is shown as-is. Entry and exit can be switched off; only deleting them is forbidden.
  4. With more than one door, the lock panel lists every door: label, state, countdown, last action, and unlock/lock per door for the same role as today's buttons (admin). With a single door it looks and behaves exactly as today.
  5. Door "main" keeps `lock_state` / `lock_countdown`. Other doors use `door_lock_state` / `door_lock_countdown`. `/api/lock/states` is polled only when SSE is not available.
  6. Unit tests cover the new pure helpers (gate patch builder, door-state reducer for SSE events), plus source checks of the wiring.
- **Scope explicitly excluded:** backend routes, `server.ts`, `src/server/**`, `src/types.ts`, shared agent context, `DoorConfigPage.tsx` (it already has its own per-door lock section), the Navbar/FaceScanner/CameraDashboard/MobileCompanion views of the main lock.

- **Files changed:**
  - `src/utils/gates.ts`: `isGateEnabled`, `GATE_OFF_BADGE`, `buildSetGateEnabledRequest`, `gateScalarsForSave`, `disableGateConfirmText`, and `GateAction` gains `"enable" | "disable"` (with done/not-done texts). `GatePatch` already had `enabled`.
  - `src/components/CameraStreamConfigPage.tsx`: the switch, the confirmation dialog, the tab badge, an overview note listing switched-off gates, the read-only state for every role, and the save payload.
  - `src/utils/doorLocks.ts` (new, pure): `readLockStates`, `interpretLockStatesResponse`, `reduceDoorLocks`, `showDoorList`, `lockStateText`, `relockPercent`, `LOCK_STATES_URL`, `DOOR_LOCK_POLL_MS` (5 s), `LOCK_PANEL_SOURCE`.
  - `src/components/SmartLockCard.tsx`: new `DoorLockList` sub-component and optional props `doorLocks`, `doorLocksNotice`, `onDoorLockState`. The single-door JSX is unchanged; it is only wrapped in a conditional.
  - `src/App.tsx`: door list (`useReducer`), `fetchDoorLocks`, new SSE listeners, `sseLive` flag, poll fallback.
  - `tests/gateSwitchUi.test.ts`, `tests/doorLocksUi.test.ts` (new); `tests/nGatesUi.test.ts` (one count).
- **Behavior changed:**
  - Gate switch (admin, N-gate server only):
    - Lives in "Thông tin cổng". It is a `role="switch"` button with `aria-checked`, labelled and described.
    - OFF opens an `alertdialog` (`ModalDialog`: focus trap, Escape, focus return) with the plain warning text. "Hủy" gets autofocus.
    - ON is sent immediately.
    - The page applies only a 2xx `success: true` answer (it uses the server's returned `config`). For 4xx/5xx it shows the server's `error` text verbatim, followed by "<gate> CHƯA được tắt/bật."; status 0 shows "Không kết nối được máy chủ…". The outcome goes to the existing `role="status" aria-live="polite"` region.
  - Read-only state: on an N-gate server, the old local "Trạng Thái Kích Hoạt Cổng" toggle becomes a read-only badge for every role, with the hint "Chỉ Quản trị bật/tắt được cổng." An older server (no `gates[]`, no `PUT /api/gates`) keeps the old local toggle, saved by "Lưu Cấu Hình", exactly as before.
  - Tabs and overview: a gate with `enabled: false` shows an amber "Đang tắt" badge in its tab instead of the green dot. The overview, which lists enabled gates only, adds a line naming the switched-off gates.
  - "Lưu Cấu Hình" on an N-gate server no longer sends gate `enabled` (`gateScalarsForSave`). This stops a page loaded before an admin's switch from silently undoing it.
  - Lock panel: shows the door list when `/api/lock/states` returns more than one door. Each row shows the label (falls back to `doorName`, then the id), the id, the state badge, the auto-relock bar with "Tự khóa sau: Ns", and "Thao tác cuối: <time> · <by>".
    - Unlock/lock buttons per door appear for admin only (`canOperateDoor`, unchanged). They send `POST /api/lock/unlock|lock { doorId, source: "Bảng Điều Khiển Khóa Thông Minh" }`.
    - Outcomes go through the existing `interpretLockCommand` into a polite live region.
    - The list has no demo/client fallback: a refusal is never shown as an opened door.
  - Single door, or an older server (`/api/lock/states` → 404): the panel is identical to before.
  - App:
    - `lock_state` / `lock_countdown` still set `lockState` exactly as before, and also update door "main" in the list.
    - New `door_lock_state` / `door_lock_countdown` listeners sit on the same single `EventSource`. The reducer only accepts a door event that names a valid door, and a `lock_*` event only for door "main", so neither can be misread as the other.
    - A door that appears via `door_lock_state` after the list loaded is appended. Events alone never create a list.
    - The list is reloaded when SSE reconnects, after sign-in, and on the refresh button. It is cleared on sign-out.
    - Polling of `/api/lock/states` every 5 s runs only while the server's event stream is not open AND more than one door is listed. It is not used for Netlify/static hosting without a backend.
    - A refusal or lost connection while loading keeps the last list and shows the reason above it.
- **API/event contracts added or changed:** none. The UI consumes the existing `PUT /api/gates/:gateId`, `GET /api/lock/states`, `POST /api/lock/(un)lock`, and the SSE events `lock_state`, `lock_countdown`, `door_lock_state`, `door_lock_countdown`.
- **Schema/migration changed:** none.
- **Environment/configuration changed:** none.

  - No new browser storage. No tokens or credentials are read or kept.
  - Door commands remain server-side and admin-only (the server enforces this; the UI hides the buttons).

## Risks and follow-up

- **Known risks:**
  - A successful switch replaces the page's config with the server's returned config, so unsaved local edits on the camera page (gate camera name, auto start, global settings) are dropped. The existing "Lưu thông tin cổng" and delete flows already behave this way.
  - Polling adds one `GET /api/lock/states` every 5 s per open dashboard, only while SSE is down and only with 2+ doors.
  - The door list's main row and the Navbar's main lock come from the same SSE events. While SSE is down, only the list is refreshed by polling. The Navbar/FaceScanner main lock is refreshed as before, by the refresh button only.
  - Switching a gate on reports "đã bật". Whether it actually scans again also depends on the gate's own watch setting.
- **Unresolved questions:** none blocking.
- **Dependencies on other agents/commits:** none.
- **Requested integration action/order:**
  1. **Backend gap (server.ts, INT/backend owner):** `POST /api/camera-streams/config` is an operator route, but `applyGateConfigPatch` still applies a gate's `enabled` from the body (`...rest`). An operator can therefore switch a gate on/off without going through the admin-only `PUT /api/gates/:gateId`. Proposal: drop `enabled` in `applyGateConfigPatch` for an N-gate config, the same way `doorId` and `pipelineMode` are already dropped, and keep `PUT /api/gates/:gateId` as the only writer. Add a negative test: an operator POST with `gates[].enabled=false` leaves the gate enabled. The UI already stops sending `enabled` there.
  2. Optional backend nicety: on SSE connect, also send `door_lock_state` for every non-main door. The UI does not need it, because it reloads `/api/lock/states` on connect/reconnect.
  3. Optional type (src/types.ts owner): a shared `DoorLockStateView = SmartLockState & { doorId: string; label: string }` for the `/api/lock/states` rows. The UI currently defines `DoorLockRow` locally in `src/utils/doorLocks.ts`.
  4. Merge order: `45fedd4` then `20f29c1` (independent; either order works). Rerun the Docker gates on the integrated branch, then do the manual dev check above before any staging deploy.
